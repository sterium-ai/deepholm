# Terrain autotiling

How ground transitions (prairie grass against water and rock) are drawn,
and how the terrain sheet is laid out. Read this before any task that
touches `game/assets/generated/`, `terrain_tileset.tres`,
`tile_atlas_map.gd` or the terrain layers of `map_view.gd`.

The terrain sheet is generated by `tools/generate_placeholder_art.py` and
registered in the TileSet by `game/scripts/tools/build_terrain_tileset.gd`.
Cell size is 16x16 with no margin or separation; `(column, row)` coordinates
are zero-based from the top-left of the PNG, columns to the right, rows
downward.

## The idea: base layer + alpha overlay, never a baked atlas

The prairie grass is drawn as an **overlay with transparent regions**: where
an overlay cell is transparent, *whatever lies underneath* shows through. So
the map is rendered as two terrain `TileMapLayer`s over the same grid:

1. **Base layer** — one fully opaque fill per tile (grass variant, water,
   rock, floor, plowed soil, planted, trench, or the ground base of a
   hazard/tree tile). Never has holes.
2. **Grass overlay layer** — one of the 12 directional grass blob cells,
   chosen per boundary soil tile from its 8 neighbours. Where the overlay
   cell is transparent, the base layer shows through, so the irregular
   bank is the overlay's own drawing of the boundary.

Consequences that are not negotiable:

- **Do not composite** base and overlay pixels into a new baked atlas at
  build time or at runtime. It multiplies the atlas by every base/overlay
  pair and hides the layering from the tileset, so tests can no longer
  check cells individually.
- **Change art in the generator, not in the PNG.** Edge cells are produced
  by `generate_placeholder_art.py`; hand-edited pixels would be lost on the
  next regeneration.
- The TileSet maps atlas cells to tile kinds; the viewer code only decides
  *which kind* each map tile is and which blob configuration its
  neighbourhood selects.

## Terrain sheet layout

`terrain.png` is 5 columns x 7 rows of 16x16 cells. Each blob cell is named
by the side (edge) or quadrant (corner) where grass is **absent**, i.e. where
the foreign neighbour shows through:

| Cell | `(column, row)` | Grass coverage |
| --- | --- | --- |
| edge N / S / E / W | (2,4) / (2,0) / (0,2) / (4,2) | everywhere except a wavy band along that side |
| convex corner NE / NW / SE / SW | (1,3) / (3,3) / (1,1) / (3,1) | only the quadrant opposite the named corner (both adjacent sides exposed) |
| concave corner NE / NW / SE / SW | (1,4) / (3,4) / (1,0) / (3,0) | everywhere except a small rounded bite at the named corner |
| unused | every other cell in rows 0-4 | fully transparent |
| grass variants 0 / 1 / 2 | (0,5) / (1,5) / (2,5) | full, opaque |
| trench, built floor | (3,5), (4,5) | full, opaque |
| plowed soil, planted base, hazard base, forest floor | (0,6), (1,6), (2,6), (3,6) | full, opaque |

Water and rock are separate opaque 16x16 files (`water.png`, `rock.png`).
Every blob cell has a 1 px darker rim where grass meets transparency, so the
bank reads as an outline against water or rock.

The blob has 12 directional cells plus full fills, the "13-cell blob". It
is **not** the 47-tile blob: combinations such as "edge N + concave SE" have
no dedicated cell, and channel/cap/isolated configurations approximate to
the highest-priority edge or corner (N > E > S > W; see ADR 021). Do not
synthesise the missing cells at runtime.

The coordinates above must match three places: the `layout` table in
`tools/generate_placeholder_art.py`'s `build_terrain()`, the registered
cells in `game/scripts/tools/build_terrain_tileset.gd`, and
`tile_atlas_map.gd`'s `GRASS_EDGE_COORDS`, `GRASS_CORNER_COORDS`,
`GRASS_CONCAVE_COORDS` and `TILE_SOIL_VARIANTS`.
`test_grass_shore_bitmask.gd` checks each configuration against literal
expected coordinates, so a swapped convex/concave pair fails the test
instead of passing it self-referentially.

The boundary is deliberately irregular: an edge cell's band wobbles by a
few pixels along its length. Check a cell by dumping
its alpha, not by guessing from the label:

```gdscript
var img := Image.load_from_file("res://assets/generated/terrain.png")
for y in 16:
    var line := ""
    for x in 16:
        line += "#" if img.get_pixel(col * 16 + x, row * 16 + y).a > 0.0 else "."
    print(line)
```

## Backing: what shows through the overlay

A boundary soil tile's base cell is not grass: it is the opaque cell of the
neighbour whose material the overlay exposes (water or rock). The same
selection that picks the overlay cell picks the backing
(`grass_shore_selection()` / `grass_shore_backing_offsets()`), so the two
layers can never disagree. When a convex corner's two sides are different
materials, the backing follows the compass priority N > E > S > W. Interior
soil tiles draw no overlay and keep a plain hash-selected grass variant as
their base.

Water and rock tiles never change cell based on their neighbours: all the
shoreline shape comes from the grass overlay on the adjacent soil tiles.

## Why a code-side bitmask instead of Godot terrain sets

Godot 4 `TileSet` terrains (*Match corners and sides*) could pick blob
cells from peering bits, but the viewer also has to pick a *backing* cell on
a different layer from the same decision. Keeping the selection in
`tile_atlas_map.gd` makes both choices one pure function of the 8
neighbours, testable headless without painting a `TileMapLayer`.

## Invalidation rule (the part the simulation must respect)

A map tile's overlay and backing depend on its 8 neighbours. When one tile
changes kind (dig, chop, till, trench, mining, building ...), the viewer
re-evaluates **that tile and its 8 neighbours**; nothing else. The dirty-cell
path in `map_view.gd` gives the changed tiles; the terrain layers expand
each to its 3x3 block before repainting. Repainting the whole layer per tick
made the map unusable during play (#345), so never do that.

## What a terrain task must deliver

1. Generator changes in `tools/generate_placeholder_art.py` (never hand
   edits to generated PNGs), with the regenerated files under
   `game/assets/generated/`.
2. A rebuilt `terrain_tileset.tres` produced by
   `game/scripts/tools/build_terrain_tileset.gd`, and a headless test that
   loads the tileset and asserts, for each registered cell, that it exists
   and is opaque/transparent where expected (alpha checks on the atlas, as
   in the dump above).
3. Updated coordinate tables in `tile_atlas_map.gd` and literal-coordinate
   cases in `test_grass_shore_bitmask.gd` when the blob layout changes.
