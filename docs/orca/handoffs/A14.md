# A14 handoff: data-driven work effects

> **In short:** What dig, chop, mine, forage, till and sow do when their `work` toil finishes
> is now an `effects` block on their `jobs.json` entry (tile check, input consumed, tile
> transform, object cleared, items always yielded with a placement, ground berries, find
> table). `ToilBindings._toil_on_work_complete()` no longer has a branch per kind: one static
> `ToilBindings.apply_work_effects()` applies the block. `spawn_wood_item()` and
> `spawn_stone_item()` are gone; every yield is `ItemTable.spawn_item(item_id, …)`. The find
> roll reads the table of the completed job's own kind. Behaviour is unchanged: the scenario
> probe produces the same saves, event log, per-5-tick trace and `state_hash()` as `main`, byte
> for byte (0 of 13 files differ). The new `test_work_effects_content.gd` adds two work kinds
> that no code names, from a fixture content bundle only, and checks their effects.
> Rules: [ADR 051](../../decisions/051-data-driven-work-effects.md).
> **Review round 1: APPROVE** (`.orca-review.md`, Codex), no blocking findings. Its two
> non-blocking notes need no code change (see "Review round 1").

## The change

`jobs.json` now says, for the six kinds (exact text in the diff):

| Kind | requires_tile | consumes | set_tile | clear_object | yields |
| --- | --- | --- | --- | --- | --- |
| dig | soil | | trench | | adjacent: always `sand`, find_table (unchanged 5/20/10/10/55) |
| mine | rock | | floor | | target: always `stone` |
| chop | | | soil | | target: always `wood` |
| forage | | | floor | true | target: `ground_berries: 1` |
| till | soil | | plowed_soil | | |
| sow | plowed_soil | seed | planted | | |

`apply_work_effects()` applies the fields in one fixed order: `requires_tile` (mismatch →
`invalid_target`/`resubmit_order`), `consumes` (none left → `blocked_missing_input`/
`resubmit_order`), `set_tile`, `clear_object`, each `always` item at the placement,
`ground_berries`, then one staged find if there is a `find_table`. That is the order each of
the six old branches used, statement for statement. A refusal returns before anything changes,
and `_toil_on_work_complete()` fails the job exactly as the old branches did (same reason,
remedy, `fail_job`, early return without the tile hooks or `resolve_giver_association`).
What did not move:

- The trench-trap check still runs first, and the water-cache/dirty/region/room hooks still
  run after, only when the tile changed.
- site_work, sleep, escape_trench and rescue keep their `match` branches: their completion
  belongs to `ConstructionSystem`, `NeedsSystem` and `TrenchSystem` (ADR 051, decision 6).
- Berries stay a per-tile counter (`spawn_berries_item()` kept): `eat_food` reads the counter,
  so folding them into an item would change behaviour. This is the "where behaviour allows"
  of the entry.
- Placement "adjacent" is ADR 026's `dig_item_placement()`, evaluated at the same moments as
  before (the always yields at completion, after `set_tile`; the find at resolve time).

Registry checks (all typed, all naming `jobs.json`): an unknown tile id in
`requires_tile`/`set_tile` or an unknown item id in `consumes`/`always`/`find_table` →
`dangling_reference`. Effects without a `work` toil, a `placement` other than
`target`/`adjacent` (the schema's `enum`, enforced since A13), a missing `placement` (schema
`required`), or `find_table` weights not summing to 100 → `schema_violation`.

changed function, so the same file runs on both trees.

  (also 0 of 13 against `075c4a5` before the rebase)
  (8 saves, `states.json`, `trace.json`, `results.json`, `io.json`, `events.json`).

  `scenario_dump: results=198 applied=108 rejected=5 events=1533 carrying_lines=163 tool_held_lines=224 items_end=36 tools_end=2 sites_end=3 save_refused=[] hash=1827253449`
- What it exercises (job statuses across the trace): completed dig 5, chop 3, mine 3,

- `test_dig_find_distribution` (1000 real seeded digs, the 5/20/10/10/55 distribution, the
  placement rule, job-id resolution order) passes unchanged except for the two adaptations
  listed above.

**2. A test adds a new work kind via content only.** `test_work_effects_content.gd` copies
the real `res://content/*.json` into `user://` (as text: a Godot JSON round trip would turn
integers into floats) and appends two kinds that appear nowhere in code:

- `quarry`: requires rock → floor, clears the object, yields `stone` and `flint` adjacent and
  has a `find_table` of `coal` at weight 100.
- `press`: requires floor, consumes `seed`, → planted, yields 2 ground berries at the target.

The fixture registry loads valid. The test builds a world on it (A13's session registry) and
runs the blocks on that world's own `TileGrid`, `ObjectTable` and `ItemTable`, through
`ToilBindings.apply_work_effects()` and `ItemTable.resolve_dig_finds()`. It checks the tile,
the cleared bush, the yields at (2, 3) in list order (the north neighbour is rock), one staged
find of kind `quarry`, which resolves to `coal` at (2, 3) with one RNG draw. A second quarry on
the now-floor tile is refused `invalid_target` and changes nothing. A press with no seed is
refused `blocked_missing_input` and leaves the tile alone. With a 2-seed stack on the ground,
it consumes exactly one, plants the tile and adds 2 berries. The test also checks the nine
registry failures above (each code, file and the offending id/rule in the message) and that
the six real kinds declare the effects in the table above.

What "content only" does not cover yet, and is outside the owned paths: the player cannot
*order* a new kind. `area_orders.gd`, `command_checks.gd`, `order_handler.gd` and
`command_router.gd` still list the six kinds by name. Also, `ToilExecutor` reads
`res://content/jobs.json` from disk rather than the session registry. A full `tick()` run of a
fixture kind therefore never reaches its work toil. The test drives the effect step itself,
not a whole job.
