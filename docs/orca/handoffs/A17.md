# A17 handoff: story and quest layer, design ADR

> **In short:** Docs only. This change adds
> [ADR 045](../../decisions/045-story-layer.md), which designs story beats and quests as
> content rules: trigger, then conditions, then effects. One story giver (job-giver pattern,
> ADR 011) evaluates the rules once per tick, and every effect is an ordinary command sent
> through `apply()`. Flags, quest stages, pending triggers and the scenario outcome are
> persisted module state, and an incident is one effect kind (`spawn_incident`). The ADR has a content schema sketch, three worked examples
> (a migrant chain, a raid warning, a first-winter quest) and the list of code tasks it would
> create. `extension-points.md` gains a "Story rule" entry marked *proposed*. No code,
> content, schema, test or save format changed. Review round 1 is answered below. Of its four
> blocking findings, three are fixed in the ADR. The fourth, owner sign-off, is **still open**:
> the owner was asked on 2026-10-27 and answered "Aún no lo apruebo" (not yet).

## Contract impact

- **Added:** ADR 045 (proposed). It decides the model (rules, flags, quests), the content shape
  (`story.json`, `quests.json`, a closed fact vocabulary, `$event` bindings, cross-checks), the
  effect whitelist (two existing commands plus four new ones), intake (an `EventLog` listener
  into a persisted, capped trigger inbox), the evaluation order (last tick phase, trigger-first,

## What the ADR found in the code (checkable)

Gaps the worked examples exposed, each turned into a code task in the ADR:

- `incident_started` is emitted at **proposal** time while the actor is still staged and not in
  the roster (`incident_scheduler.gd` `_spawn()` vs `activate_pending()`), so `set_faction` on a
  just-proposed migrant would be rejected by `check_set_faction_command()`'s `_find_colonist`
  check (`command_checks.gd:212`). Hence the new `incident_actor_arrived` event (task S5).
- The core has no death event (`grep -rn "died" game/scripts/core` finds only comments;
  `combat_resolver.gd` returns `dead_actors` and emits only `attacked_by`, and
  `world_state.gd` `_apply_actor_death()` emits no event), so the raid example polls `actor_count` on `day_start`.
- Food is not an item: berries live in the ground-berries table, not `items.json` (ids: axe,
  pick, seed, stone, sand, gold_coin, flint, coal, wood), hence a separate `food_count` fact.
- `calendar.json` has only the `sow` window and `calendar.schema.json` requires `labour` on every
  window, so a `winter` window needs a schema relaxation or the owner's pending calendar decision.
- `spawn_incident` is rejected when incidents are disabled (`command_checks.gd:224`); the ADR's
  preview-then-apply rule turns that into `story_rule_skipped` instead of a half-fired beat.

## Review round 1

Codex: `REQUEST_CHANGES`, four blocking findings, no non-blocking ones. Answered as follows.

1. **`045-story-layer.md:218`: a single cursor cannot resume a rule-first walk under the budget.**
   Fixed. Section 4 now walks **trigger-first**: each pending trigger, then the rules matching
   it in ascending id. One persisted position, `resume.afterRule`, resumes inside the head
   trigger, so eight firings by one rule can no longer skip triggers a later rule still needs.
   Only firings count against the budget. Task S3's tests now include the case the reviewer
   asked for: three rules sharing one trigger type, twelve matching events in one tick, every
   (event, rule) pair firing exactly once with no rule starved. The rejected first draft is
   recorded in *Alternatives*.
2. **`045-story-layer.md:252`: a load loses story-effect events and budget-deferred triggers.**
   Fixed. The event cursor is replaced by a **persisted inbox**. An `EventLog` listener appends
   each event that some rule's trigger matches (stored as `{type, tick, sequence, data}`), plus a
   `day_start` entry per new day. Player-command events between ticks, effects' own events and
   budget leftovers all wait in it. The inbox, `resume` and the overflow counter are in the
   `story` save key (section 5) and in `state_hash()`. A cap of 256 entries counts and reports
   any overflow (`story_inbox_overflow`), so a loss is never silent. Task S4's tests now
   compare four save/load points with an uninterrupted run: mid-quest, mid-budget, right after
   effects emitted triggering events, and after a between-ticks player command. The old
   "events can be missed" limitation is gone from the ADR's *Consequences*.
3. **`045-story-layer.md:171`: `end_scenario`'s outcome had no storage, default or hash.** Fixed.
   The outcome is owned by the story module as `story.outcome` (`{result: "" | "won" | "lost",
   tick, text}`) and read through `get_story_outcome()`. The migration default is `{result: "",
   tick: -1, text: ""}`, and the hash covers it. `end_scenario` is now one-shot: a second one is
   rejected with "The scenario has already ended", and the giver stops after an outcome. S2 and
   S4 tests cover the rejection and the restore.
4. **`A17.md:157`: owner sign-off is required, not post-merge.** Agreed: the earlier wording was
   wrong, REVIEW.md item 7 only covers native-build checks. Not resolved. On 2026-10-27 the
   owner was asked, in the author's terminal, whether they approve ADR 045 as it stands after
   fixes 1–3. Answer, verbatim: **"Aún no lo apruebo"** (not yet). The ADR therefore stays
   **proposed**, and A17's acceptance ("the owner signs off the ADR") is **not met** on this
   branch. This finding is expected to stay blocking until the owner approves. When they do, the
   change is the ADR status line, a dated sign-off line in the ADR, and this section.
