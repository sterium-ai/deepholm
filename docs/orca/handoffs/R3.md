# R3 handoff: extract `TileGrid`, `ObjectTable`, `ZoneTable`, `Passability`

> **In short:** four new core modules now own the map: `map/tile_grid.gd` (dimensions,
> tiles, water cache, dirty-cell log, lazily built regions/rooms), `objects/object_table.gd`
> (placed objects with footprints, origins, orientation, health and factions),
> `objects/zone_table.gd` (stockpile zones and their id counter) and `map/passability.gd`
> (the movement rule and the faction rules). `WorldState` delegates to them. Nothing in
> behaviour changed: a map-heavy scenario gives the same saves, event logs, per-tick map
> trace, command and `preview()` results and `state_hash()`, byte for byte, as on `main`;
> the R1 and R2 probes still match too. `world_state.gd` goes from 4667 to 4290 lines.

Each function body is the same statements in the same order. The only changes are:

- the field and function renames above (callers retargeted, e.g. `_get_regions()` becomes
  `_tile_grid.get_regions()`);
- `_width`/`_height` read as `_tile_grid.width`/`height` (inside `TileGrid`, as `width`/`height`);
- inside a module, the `WorldState` methods it used to call arrive as injected `Callable`s or go
  through a sibling module:
  - `TileGrid` gets `passability`, `get_object` and `_zone_table.is_in_any_zone` for the
    region/room maps (it is built before `Passability` and `ObjectTable` exist, so it holds the
    `WorldState` methods as `Callable`s, which resolve at call time);
  - `ObjectTable` calls the sibling `TileGrid` for `mark_dirty()`, `get_regions()` and
    `get_rooms()`, in the same places and order as before;
  - `Passability` reads the sibling `TileGrid` (`width`/`height`, `get_tile()`, `get_regions()`)
    and `ObjectTable` (`get_object()`), and gets `_actor_faction` and `_find_colonist` as
    `Callable`s;
- `ObjectTable.decode()` is the loop that used to sit in `StateCodec.decode()`, with
  `world._object_footprint_tiles()` now `object_footprint_tiles()` and its locals renamed
  `decoded_*` (they would otherwise shadow the members).

No module stores or receives `WorldState`. They are built in `_init()` right after the map size
is resolved and before anything reads tiles or objects: `ZoneTable.new()`,
`TileGrid.new(width, height, passability, get_object, _zone_table.is_in_any_zone)`,
`ObjectTable.new(_object_definitions, _tile_grid)`,
`Passability.new(_content, _tile_grid, _object_table, _object_definitions, _tile_definitions,
_actor_faction, _find_colonist)`. `_object_definitions` and `_tile_definitions` stay in
`WorldState` (the construction code and tests still read them) and are shared by reference,
never reassigned after `_init()`.

The callables handed to GlobalAssignment, CombatGiver, ApproachGiver, IncidentScheduler,
HaulGiver, ConstructionGiver, ItemTable, CombatResolver and `scheduler.tick()` now point at the
module methods (`_passability.is_passable`, `_zone_table.is_in_any_zone`,
`_tile_grid.get_regions`, `_object_table.damage_object`...). Public-name callables
(`passability`, `get_object`, `get_objects`, `get_zones`...) keep pointing at `WorldState`'s
delegations, so no giver or toil file changed.

**Kept in `WorldState` on purpose** (listed in `REFACTOR-PLAN.md`'s approximate R3 row):

- `is_cell_free()`, `_is_cell_occupied()` and `_is_bare_tile()` join four tables at once
  (reservations, colonists, ground items, tool items, zones, objects). Moving them into one of the
  new modules would hand it references to all the others; they stay façade glue until R11/R12.
- `_tile_key()` and `_cell_key()` are `JobQueue`/`ReservationTable` key formats, not tile-grid
  state.
- `_actor_faction()` and `_actor_may_reserve_target()` read actors and incidents (not R3).
- Code that later tasks extract keeps writing tiles directly through the grid:
  `_toil_on_work_complete()` (R11) mutates `_tile_grid.tiles[...]` and then calls
  `update_water_tile_cache()`, `mark_dirty()` and the region/room updates, exactly as before;
  `_spawn_colonists()` seeds berry bushes into `_object_table.objects`/`object_factions` as
  before.

**Viewer:** no viewer file read a moved private member, so none changed.

## Contract impact

- No schema bump, migration, ADR or contract change. The `test_save_migration` fixtures are
  untouched.
- **Save format:** the same keys, nesting and values as before:
  - `map` = `{width, height, tiles, generatorVersion}` (only `tiles` comes from `TileGrid.encode()`);
  - `objects` = `[{target, kind, factionId, orientation?, health?}]`, one per origin tile;
  - `zones` = `[{id, x, y, width, height}]` and top-level `nextZoneId`.

  Key insertion order in `StateCodec.encode()` is unchanged, and `decode()` restores each field at
  its old position. The identical `save_*.json`/`state_*.json` below confirm it.
- **`state_hash()` coverage for these modules** (`R3-hash_coverage.gd` changes one field at a
  time; `main` and the branch print the same 12 lines):
  - Included (unchanged): `tiles`, `width`/`height`, `objects`, `object_health`, `zones`,
    `next_zone_id`. These are now written by each module's `hash_into()`; `JSON.stringify` sorts
    keys, so the insertion order does not affect the hash.
  - Deliberately excluded (unchanged): `object_factions`, `object_origin`, `object_orientation`,
    `dirty_cells`, `water_tile_cache`, and the region/room maps.
  - `Passability` holds no state.
- **Invariants from trimmed comments** are now in each module's class doc:
  - `TileGrid`: row-major indexing; width/height only change through `decode()`, before the
    tiles; regions, rooms and the water cache are built lazily so a decode never leaves them
    stale, and are kept in sync afterwards; the dirty-cell log is append-only, never cleared,
    never persisted, and colonist/item movement never appends to it; what is hashed.
  - `ObjectTable`: which maps carry an entry on every footprint tile and which only on the
    origin; factions/health/orientation are parallel maps because the codec assumes a plain kind
    String; orientation absent (never `""`) when unrotated; `set_object()` is the only mutator and
    always marks dirty and updates regions/rooms; what is hashed and why hp must be.
  - `ZoneTable`: ids never reused; zones are rectangle bookkeeping, never reservations; what is
    hashed.
  - `Passability`: the one movement rule, out-of-bounds/unknown kind impassable, `faction_id`
    only matters for doors, every faction rule fails open on an unknown faction.
