## Diagnosis: the rescue key that writes an out-of-map tile

Not fixed here (REFACTOR-PLAN rule 7); reproduced by `R4-scenario_dump.gd` on `main` and on the
branch alike (`save_refused=["600:schema_error invalid tile coordinates", "700:..."]`).

1. **Where the key is made.** A `rescue` job's work toil calls `WorldState._set_work_progress()`
   → `WorkProgress.record()` (on `main`: the same lines inside `_set_work_progress()`). It computes
   the key with `key(x, y)`, which finds the tile's reservation owner and, because that job's kind
   is `rescue`, returns `key_for_job()`'s job-scoped form `"<job_id>:<x>_<y>"`, e.g.
   `"job_120:44_33"`. `record()` writes that key into **both** `progress` and `owners`
   (`owners["job_120:44_33"] = "job_120"`).
2. **Where the tile goes wrong.** `StateCodec._encode_work_progress()` handles the job-scoped form
   (it splits on the last `:` and writes `ownerJobId`), but
   `StateCodec._encode_work_progress_owners()` does `String(key).split("_")` without stripping the
   `job_id:` prefix: `"job_120:44_33"` → `["job", "120:44", "33"]`. `int("job")` is `0` and
   `int("120:44")` is `12044` (Godot's String→int skips the non-digit `:`), so the entry becomes
   `{"target": {"x": 0, "y": 12044}, "jobId": "job_120"}`. R2's `job_172` at `(44, 0)` gave the
   `{x: 0, y: 17244}` quoted in `R2.md` the same way (checked with a two-line Godot script:
   `"job_172:44_0".split("_")` → `x=0 y=17244`).
3. **Why the save is refused.** `SaveIO.write_atomic()` validates every `workProgressOwners`
   target against the map and stops with `schema_error: invalid tile coordinates`. In the probe:
   at tick 600 the state holds `workProgress` `{ownerJobId: job_120, target: (44,33),
   ticksRemaining: 7}` and the bad owner `{x: 0, y: 12044}`; at tick 700 the same for `job_151`
   (`y: 15144`). Both are active `rescue` jobs.
4. **What happens in memory.** `to_save_state()`/`from_save_state()` (no `SaveIO`) does not fail:
   `_decode_work_progress_owners()` turns the bad entry into the key `"0_12044"`, which matches no
   progress key, so `restore_owners()` ignores it; `reconstruct_owners()` then recovers the owner
   from the rescuer's `work.job_id`, giving back `"job_120:44_33"`. So only writing to disk breaks,
   but every save taken while a rescue is mid-work is lost.
5. **Suggested fix (for the follow-up task):** encode owners like `_encode_work_progress()` does
   (split on the last `:`, write `ownerJobId`) and decode them back to the scoped key; this adds an
   optional field to `workProgressOwners`, so it needs the schema entry, `SaveIO` validation, a
   migration decision and a fixture; plus a test that saves through `SaveIO` mid-rescue.
