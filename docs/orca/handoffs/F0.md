## What changed

Design (owner, 2026-10-29, BACKLOG F0), implemented line by line:

| Design line | Implementation |
| --- | --- |
| 3 days per month, 12 months per year (a year = 36 days of 2,200 ticks) | `calendar.json` gains `days_per_month: 3`, `months_per_year: 12`; `day_length_ticks` stays 2200 |
| Day numbering stays as today; month and year derived; no save change | `day_of_tick()` untouched. New pure queries `month_of_tick()`, `year_of_tick()`, `date_of_tick()` in `CalendarService`. Nothing stored, hashed or saved |
| Windows may be declared by month range as well as by day range; `sow` stays as declared | A window declares `from`/`to` or `from_month`/`to_month`. `CalendarService` converts a month range once, at load, to `(from_month - 1) * 3 + 1 .. to_month * 3`. Every query reads only `from`/`to`. `sow` is still `from: 1, to: 20` |
| Viewer shows "day D · month M · year Y" and the window label | `InfoPanel.date_label`, the first line of the information column: "Day 1 · month 1 · year 1 · sowing window" (text keys `calendar.date_label`, `calendar.date_window_label`) |

- **`CalendarService`** (`core/calendar/calendar_service.gd`, 80 → 130 lines): `days_per_month()`,
  `months_per_year()`, `month_of_tick()`, `year_of_tick()`, `date_of_tick() -> {day, month, year,
  window_label}` (`window_label` = label of the first open window in declaration order, or `""`),
  `_with_day_range()` for month windows. Both new content numbers are optional in the schema and
  default to 1 (so the test calendars elsewhere, which set only `day_length_ticks`, keep loading).
- **Schema** (`content/schemas/calendar.schema.json`): the two numbers, `from_month`/`to_month`,
  `from`/`to` no longer required, and `oneOf` [day pair | month pair]. ContentRegistry's schema
  subset ignores `oneOf` (`content_registry.gd:360`), so it documents the rule for external tools.
  A window with neither complete pair loads but never matches a day (see limitations).
- **Snapshot** (`core/world/view_snapshot.gd`, owner-approved scope extension): `build()` reads
  the world's `CalendarService` from `sources["calendar"]` and adds `"date":
  calendar.date_of_tick(tick)`, frozen like the rest. The calendar is the world's, not the
  viewer's registry: a world given a test calendar shows that calendar's date (tested).
- **`world_state.gd`**: one existing line edited, none added (782 on main after A16b → 782):
  `get_view_snapshot()` passes `"calendar": _calendar` in `sources`. Since A16b, `_calendar` is
  built from `WorldSetup.calendar_document()`: a scenario's own calendar when it has one, else
  `calendar.json`. So the snapshot's date always follows the calendar the world runs on.
- **Viewer** (`viewer/info_panel.gd`): `date_label` above the status line, filled by
  `refresh(snapshot)` (boot's one snapshot per refresh, ADR 055), by `build()` and by
  `set_world()`. `InfoPanel.date_text()` only formats; a window label that is a text key is
  resolved through the text table, as the work table's banner does.
- **Docs**: ADR 060 (new) and its row in `docs/decisions/README.md`; `colonist-ai.md` §3.7
  (schema and queries; the old "day-of-year/spring day 1" wording replaced by "day numbers
  counted from the start", which is what the code always did); `simulation-boundaries.md` (the
  snapshot carries the date); `docs/design/baseline.md` §9 row → done, decision 1 → done.

## Known limitations

- **Windows do not repeat each year**, by day or by month: both count from the start of the
  game, as day windows always did, so `sow` (days 1-20) is open only in year 1. The closed design
  does not ask for yearly windows, and they would change behaviour after day 36 and need the
  fired-alert set to be per year (a save change). This matters for F1 ("outside the sowing window
  planted tiles do not grow"). From year 2 on there is no sowing window. **Owner decision needed**
  before or during F1.
- **A16b's scenario calendars cannot declare months yet.** A16b (#42, ADR 057) lets a scenario
  carry its own calendar document. That document's shape is a separate copy:
  `scenarios.schema.json` `calendar`, and `CalendarValidator._valid_scenario_start()` with
  `CALENDAR_FIELDS`/`WINDOW_FIELDS` for the persisted `scenarioStart`. The copy allows only
  `day_length_ticks` and day windows. A scenario calendar therefore runs with the default 1-day
  months and 1-month years, and may not use `from_month`/`to_month`. No shipped scenario declares
  a calendar (`scenarios.json` has none), so nothing changes today. Widening that copy touches
  persistence and A16b's paths (excluded here by the owner's note), so it needs an owner decision
  and its own task.
- ContentRegistry does not enforce the schema's `oneOf`. A window with only `from_month`, or a
  mix such as `from` + `to_month`, loads and never matches a day; one with both pairs uses the
  month pair.
- The viewer line is checked headless through the boot scene's `_build_ui()`/`_refresh()`. The
  owner's playtest on the native build (desktop shortcut) is pending, after merge.
