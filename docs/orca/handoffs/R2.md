# R2 handoff: extract `ItemTable`

> **In short:** `game/scripts/core/items/item_table.gd` now owns the ground items and their
> id counter, the item factions, the ground berries and their factions, and dig's find roll
> with its own injected seeded RNG. `tool_item_store.gd` moved under `items/` unchanged.
> `WorldState` delegates to the new module. Nothing in behaviour changed: an item-heavy
> scenario gives the same saves, event logs, per-tick item trace, command results and
> `state_hash()`, byte for byte, as on `main`. The R1 scenario also still matches.

Each function body is the same statements in the same order. The only changes are:

- the field renames above;
- WorldState methods and fields are reached through injected `Callable`s:
  - `passability`, `get_tile`, `_is_in_any_zone`;
  - `_scheduler.queue.get_reservation_table` (called on every use, because
    `queue.restore()` replaces the table on load);
  - `_fail_haul_jobs_referencing_item`, `_cancel_haul_job_carrying_consumed_item`;
  - a lambda that returns the live `_colonists`, because `decode()` replaces that array;
- `TILE_TRENCH` is read as `ContentRegistryType.TILE_TRENCH`, which is the same constant
  `WorldState.TILE_TRENCH` aliases.

`_fail_haul_jobs_referencing_item()` and `_cancel_haul_job_carrying_consumed_item()` are
job-lifecycle code that the task does not list, so they stay in `WorldState` and are injected
as callbacks.

New code in the module, each piece taken from a block that already existed:

- `has_item_at(x, y)` is the item loop that `_is_cell_occupied()` and `_is_bare_tile()` each
  contained. Both now call it in the same position, with the same early return.
- `stage_dig_find(job_id, x, y)` replaces the inline `_pending_dig_finds.append({...})` in
  `_toil_on_work_complete()`. The dictionary it appends is the same.
- `consume_ground_berry(x, y)` is the eat_food decrement block from `_apply_need_effect()`,
  moved as it was.
- `_drop_inventory_item()` used to mint an id inline (`"item_%d" % _next_item_id`, increment,
  `_place_ground_item`). It now calls `place_new_ground_item()`, which runs those three
  statements and returns the id. The caller ignores the returned id.
- `encode()`, `decode(state)` and `hash_into(snapshot)` handle persistence and the hash (see
  below).

Code that later tasks will extract keeps reading the table directly: `_need_source_candidates()`
(R8) reads `_item_table.ground_berries`, and `_next_site_fetch_source()` (R5) reads
`_item_table.items`.

`ItemTable.new(content, dig_find_random, colonists, passability, get_tile, is_in_any_zone,
reservation_table, fail_haul_jobs_referencing_item, cancel_haul_job_carrying_consumed_item)` is
built in `_init()` right after `_event_log`, before anything that reads items. The module has no
reference to `WorldState`. `ToilExecutor` gets `_item_table.item_lookup`,
`.remove_ground_item_units` and `.place_new_ground_item` in place of the three old WorldState
callables. `HaulGiver`, `ConstructionGiver` and `CalendarAlertGiver` keep their old callables,
which now delegate, so no giver or toil file changed.

**Viewer compatibility.** `viewer/debug_scenario.gd` is outside R2's owned paths. It seeds farm
stock through `world._items[...]` and `world._next_item_id`. To keep it working, `WorldState`
keeps those two names as accessor properties that read and write the table (`_items` has a
getter; `_next_item_id` has a getter and a setter). Nothing else uses them: core code and tests
call `_item_table` directly. They can be removed once the viewer stops writing private fields
(R13 or a viewer task).

## Contract impact

- No schema bump, migration, ADR or contract change. The `test_save_migration` fixtures are
  untouched.
- **Save format:** the same keys, nesting and values as before:
  - `items` = `{nextId, list[{id,x,y,kind,count,factionId}]}`;
  - `groundBerries` = `[{target, berries}]`;
  - optional `digFindRng` = `{seed, state}`.
  `decode()` now restores `groundBerries` and `digFindRng` together with `items`, at the old
  `items` position, instead of later. Nothing in `decode()` between those points reads berries
  or draws from the dig-find stream. The identical `state_800.json` below confirms this.
- **`state_hash()` coverage for this module** (`R2-hash_coverage.gd` changes one field at a
  time; `main` and the branch print the same lines):
  - Included (unchanged): `items`, `next_item_id`, `dig_find_rng` (seed and state). These are
    now written by `ItemTable.hash_into()`. `JSON.stringify` sorts keys, so the insertion order
    does not affect the hash.
  - Deliberately excluded (unchanged): `item_factions`, `ground_berries`,
    `ground_berries_factions`, `pending_dig_finds`.
  - `_object_health` stays in `WorldState` (R3) and is still included.
- **Invariants from trimmed comments** are now in `ItemTable`'s class doc:
  - items have a fixed shape, with factions kept in a parallel map;
  - every spawn takes its id from `next_item_id`;
  - the ground-berries key format, dropped at zero;
  - what is hashed and what is excluded;
  - ground-berries factions are never persisted;
  - dig finds are staged during a tick and drained in ascending job-id order, never saved;
  - one RNG draw per roll.

  The stale comment "persisting faction_id is future work" was dropped: `factionId` has been
  persisted for some time.

## Known limitations

- **Godot path:** this session did not inherit `$env:GODOT`. It is set at user level, so Orca
  was probably started before it was set. Every Godot command passed the explicit path.
- **Re-import churn (R0b):** `--import` rewrites 31 `game/assets/generated/*.png.import` files,
  changing only their line endings. None of them are committed.
- **Pre-existing bugs found by the probe.** All three behave the same on `main`, so they are
  not fixed here (REFACTOR-PLAN rule 7). They are added under *Parked* in `BACKLOG.md`.
  1. `StateCodec._encode_work_progress_owners()` splits a `rescue` job's job-scoped key on
     `_`, which writes `{x: 0, y: 17244}` for `job_172`. `SaveIO.write_atomic()` then refuses
     the tick-800 save with `schema_error: invalid tile coordinates`. This is R4's area.
  2. `state_hash()` does not include ground berries.
  3. Ground-berries factions are not persisted, so they read `""` after a load.
- **Stale references outside the owned paths** (left for a docs task):
  - `docs/architecture/orders-and-movement.md:294` and `save-system.md:526-569` still name
    `WorldState._dig_find_random`, `_items`, `_item_factions` and `_next_item_id`;
  - `docs/decisions/013-tool-toils.md:10` still names `jobs/tool_item_store.gd`;
  - comments in `save_io.gd`, `save_migrations.gd`, `toil_executor.gd:386` and
    `calendar_alert_giver.gd:31` still name the old WorldState members. The functions those
    comments describe still behave as described.
- The `_items`/`_next_item_id` accessors on `WorldState` exist only for
  `viewer/debug_scenario.gd`; see "Viewer compatibility" above.
- **Exit-time leak counters** go up by one per world, from the `ItemTable` script and instance
  held through bound `Callable`s, like R1's `EventLog`. No new Godot warnings or errors appear
  otherwise.
