## Moved out of `WorldState`

Everything moves to `CombatSystem` (`world._combat_system`). Names called from outside the
module lose the leading `_`; names used only inside it keep it.

| From `WorldState` | To `CombatSystem` |
| --- | --- |
| `var _combat_status` | `combat_status` |
| `const REASON_FIGHTING` | same name; `WorldState` keeps it as an alias |
| `_apply_combat(tick)` | `apply_combat(tick)` (called by `tick()`, `bench_common.gd`) |
| `get_actor_combat_reason()` | same name; `WorldState` keeps a one-line delegation (public surface: tests, viewer) |
| `_apply_actor_death()` | `apply_actor_death()` (tests call it directly) |
| `_cleanup_actor_scheduling()` | `cleanup_actor_scheduling()` (called by `WorldState._remove_colonist_by_id()`) |
| `_cancel_job_for_death()` | `_cancel_job_for_death()` |
| `_drop_inventory_contents()` / `_drop_inventory_item()` | same names |
| `_ensure_health()` / `_ensure_combat()` | `static ensure_health(colonists, content)` / `static ensure_combat(colonists, content)` |
| `get_actors_with_health()` | same name; `WorldState` keeps a one-line delegation (public surface: `colonist_sprites.gd`, tests) |

**Why the two backfills are static.** `WorldState._init()` calls `_ensure_combat()` right
after `_spawn_colonists()`, before the scheduler, event log, item table, CombatGiver,
WorkProgress and NeedsSystem the module needs exist. Building the module there would need
lambdas for all of them; moving the call later would reorder `_init()` (and change what a
world that fails startup half-way holds). As statics taking the roster and the content
registry they run at exactly the same point. `state_hash()` and `to_save_state()` call
`CombatSystemType.ensure_health(_colonists, _content)` where they called `_ensure_health()`;
NeedsSystem, which received the two bound methods, now receives two lambdas doing the same
call (`needs_system.gd` is unchanged).

**Move, not rewrite.** [`R9-move_check.py`](R9-move_check.py) takes each of the 10 moved
functions from `main`'s `world_state.gd`, applies the listed mechanical renames and compares
the result with the body in `combat_system.gd`, statement by statement, with comment and
blank lines dropped. No statement is added or removed. The renames are:

- the new names; `_combat_status` → `combat_status`;
- `PRIORITY_TICK` → `_event_priority` (the constructor receives `WorldState.PRIORITY_TICK`);
- `get_object` / `get_object_faction_id` passed to `CombatResolver.resolve_tick()` →
  `_object_table.get_object` / `_object_table.get_object_faction_id` (the `WorldState`
  methods were one-line delegations to exactly these);
- `_remove_colonist_by_id`, `_job_restricted_to`, `_finish_job`, `_resolve_giver_association`,
  `is_tool_kind`, `spawn_ground_tool_item` → injected `Callable`s (`.call(`);
  `_approach_giver.forget(` → `_approach_forget.call(`;
- `_colonists` → `_get_colonists.call()`; in the two static backfills `_colonists` →
  `colonists` and `_content` → `content` (their parameters), and the signature line is the
  new static one.

Result: `move_check: 10 function(s), 0 differ`. Not vacuous: with
`not in ["queued"]` in `cleanup_actor_scheduling()` and `item.get("count", 2)` in
`_drop_inventory_contents()` it reports `2 differ` (tried, then restored).

**Dependencies (no back-reference).** `CombatSystem.new(content, relations, event_priority,
scheduler, progress_table, tool_store, item_table, object_table, event_log, needs_system,
combat_giver, get_colonists, approach_forget, job_restricted_to, finish_job,
resolve_giver_association, remove_colonist_by_id, is_tool_kind, spawn_ground_tool_item)` is
built in `WorldState._init()` right after `NeedsSystem` (it reads and detaches
`NeedsSystem.paused_jobs` on death). Its arguments are:

- sibling modules and services built once and never reassigned (`StateCodec.decode()`
  restores them in place): `_content`, `_relations`, `_scheduler`, `_progress_table`,
  `_tool_store`, `_item_table`, `_object_table`, `_event_log`, `_needs_system`,
  `_combat_giver`;
- a lambda returning `_colonists` (`decode()` reassigns that field) and a lambda calling
  `_approach_giver.forget()` (`_build_dimension_services()` rebuilds ApproachGiver, also
  from `decode()`);
- six bound `WorldState` methods (`_job_restricted_to`, `_finish_job`,
  `_resolve_giver_association`, `_remove_colonist_by_id`, `is_tool_kind`,
  `spawn_ground_tool_item`).

It never stores or receives `WorldState`. The construction order of every other object in
`_init()` is unchanged.

**`CombatGiver` / `ApproachGiver`.** The entry says they "depend on" the module. Neither
called a moved function: their constructor callables (`_job_restricted_to`,
`_flee_target_reserved`, `_cancel_autonomous_job`, `_actor_may_reserve_target`, ...) are not
in the R9 list of `REFACTOR-PLAN.md`, and the owner's note says to stay strictly on that list,
so their wiring is unchanged. What depends on the module is the other direction:
`CombatSystem.apply_combat()` drives `CombatGiver.advance()`, and the death cleanup calls
`CombatGiver.forget()` / `ApproachGiver.forget()`. `approach_giver.gd`'s three doc comments
that named `WorldState._apply_combat()` now name `CombatSystem.apply_combat()`;
`combat_giver.gd` names no moved function and is unchanged.

**Kept in `WorldState` on purpose:**

- `_remove_colonist_by_id()`: the one roster-removal path, shared by death, incident despawn
  (`IncidentScheduler`) and trade (`TradeSystem`); not in the R9 list. It now calls
  `_combat_system.cleanup_actor_scheduling()`.
- `_job_restricted_to()`: not in the R9 list; also injected into CombatGiver and
  ApproachGiver. Injected into the module as a callable.
- `_ensure_held_tool()`: a worker backfill, not combat (R11/R12).

### Byte identity

[`R9-scenario_dump.gd`](R9-scenario_dump.gd) uses seed 4242, a 48x48 map and incidents on.
At tick 0 it clears an 11x11 yard at the map centre, moves the 3 spawned colonists there and
adds 3 more, and starts them at mixed hp (100, 8, 45, 20, 3, 70: some below their flee
fraction, some one hit from death), mixed needs (decay sped up 25x, so need jobs and paused
jobs are live when someone dies), items in the hands of some and a held axe/pick on others.
Then:

- every 60 ticks a pair of wildlife wolves at mixed hp (some with an `inventory`) arrives
  from alternating sides; they attack, colonists flee (flee and approach jobs);
- every 100 ticks a 2/2-hp `predators` wolf (the colony treats wildlife as neutral, so it
  never hits back at those) carrying 2 stone, 2 axes and a `pick` tool slot appears next to a
  healthy colonist, which kills it: the inventory drop path (stack, tool kind with count 2,
  tool slot) runs in every segment;
- every 150 ticks a reinforcement colonist holding flint arrives;
- every 20 ticks three random orders or a `cancel_job` on a live flee/approach job, each
  previewed then applied;
- every 100 ticks the world is saved (raw and through `SaveIO`), reloaded with
  `from_save_state()`, and play continues on the reloaded copy; the event log (runtime only)
  is deep-copied right before every reload.

Every 5 ticks the probe traces every actor's position, health, combat component, hands, held
tool, inventory, work/route state and `get_actor_combat_reason()`, the raw combat-status and
paused-jobs maps, every non-terminal (and every flee/approach) job, ground items, tool items,
`get_actors_with_health()`, CombatGiver's blocked targets, ApproachGiver's job targets and
`state_hash()`, each line as a deep copy.
