# A2 handoff: allocation-free map queries (packed cost grid, integer object keys)

> **In short:** `Passability` now keeps every tile's move cost and its passable/door flags in
> packed arrays. The arrays are refreshed from `TileGrid.mark_dirty()`, the hook every tile and
> object change already calls. So `passability()` no longer formats a key, and the route cost
> callables, regions and rooms read integers without allocating. `ObjectTable` keys its maps
> by integer tile index. The `"%d_%d"` String key now exists only where the save and
> `state_hash()` are written, and their output is unchanged. `RegionMap` builds the whole map
> from row runs instead of a tile-by-tile flood. `RoomMap` skips the re-flood when a tile's
> open/door state did not change.

## How the cache stays correct

- **Built lazily**, on the first query, like regions and rooms. World construction writes the
  generated map and berry bushes before any query: `_built` is still `false` after `new()`,
  checked with a probe.
- **Refreshed at the existing mutation points.** Every core write of a tile kind or an object
  already calls `TileGrid.mark_dirty()`: `ToilBindings._toil_on_work_complete()` (the only core
  writer of `tiles[]`, per `grep "tiles\[" game/scripts/core`) and every touched footprint
  tile in `ObjectTable.set_object()`. `mark_dirty()` now refreshes that tile.
- **Dropped on wholesale replacement:** `TileGrid.decode()`, `ObjectTable.decode()` and
  `place_generated()` call `reset_cells()`.
- **Self-checking against direct `tiles[]` writes.** Each tile remembers the tile kind it was
  computed from (`_kind`). A query recomputes a tile whose `TileGrid.tiles` entry differs, and
  `passable_mask()`/`room_cell_flags()` first compare the whole array (one native `Array ==`).
  This matters because 54 test files write `tiles[]` directly, in about 360 places, many of
  them in mid-test. The first suite run without this check failed `test_rescue` and
  `test_dig_find_distribution` on stale tiles. The check keeps those tests, and any future
  writer that forgets `mark_dirty()`, correct without touching ~360 test lines.
- **Direct object writes are not detected.** After a query, a direct write to ObjectTable's
  maps must be followed by `reset_cells()`, as the class doc says. The suite contains no such
  write other than the two fixtures adapted above.

## Identical region ids

The old build ran a flood-fill from each unlabelled passable tile in row-major scan order, so
region *k* is the one whose first tile in row-major order comes *k*-th. The new build:
- labels row runs (`PackedByteArray.find()`);
- unions runs that share a column with a run in the row above (4-connectivity);
- gives each set the next id the first time one of its runs is met in run order.

Runs are created in row-major order, so the first run met of each region holds that region's
first tile. Same ids, same `_next_id`.

Split and merge keep their statements and neighbour order: the first neighbour keeps the old
id, and later unconnected neighbours take fresh ids in up/left/right/down order. Only the
visited/frontier containers changed.

Evidence: `regions.json` (all 65,536 ids of the generated seed-42 256×256 map) and the 48×48
id array in every trace line are byte-identical to `main`. `test_regions` and `test_rooms`
pass.

## Rooms without a re-flood

A room's shape depends only on which tiles are open (passable and not a door) and which are
doors. When `on_passability_changed(x, y)` finds `(x, y)`'s open/door state unchanged
(soil → plowed_soil, a bed placed or removed), a rebuild would recompute the same members,
doors and `enclosed` flag. The only thing that can differ is `has_bed`, and only through
`(x, y)` itself, so the fast path adds or removes `(x, y)` in that room's bed set. A changed
state takes the original path: neighbourhood ids before and after, clear, rebuild.

The `test_rooms` check "placing a bed on an interior tile must set has_bed true even though
passability never changed" covers the bed case and passes. The dump's room probes are
identical to `main`: a walled 5×5 room with a bed inside, its door removed at tick 260 and
restored at tick 300.

## Known limitations

- **Short route searches stay above 2 µs/expansion** (not gated, per the owner's
  clarification): d=32 is 1.81–2.38 across six runs and d=8 (79 expansions) is 2.70–3.82.
  - **Why:** a search that short is dominated by `RouteSearch`'s per-search and per-resume
    costs. Even with no map query at all (the open-grid array-cost rows), d=8 costs
    2.97–3.86 µs per expansion on either tree.
  - **The map query is no longer the cost:** it now costs about what a bare array read does.
    On long searches the generated map runs at 1.8 µs against the open grid's 1.4 µs.
  - **The fix is outside A2:** getting short searches reliably under 2 µs means changing
    `routing/route_search.gd`, which is not an A2 path. The owner placed that work under A8.
- A direct write to `ObjectTable`'s maps after a passability query is not detected by the
  cache (tile writes are). Core never does this; a test fixture must call
  `TileGrid.reset_cells()`, as the two adapted fixtures do.
- The regions split (block one tile in a large open region) still floods the old region once.
  It is faster (packed containers) but not the incremental algorithm. Not an A2 acceptance
  line.
- Rooms' full build (first `get_rooms()`) still floods every area: now about 290–370 ms on
  the generated map, against about 870–1,000 ms on `main`. Not an A2 acceptance line. A19
  deals with the region side of tick 1.
