# A2 handoff: allocation-free map queries (packed cost grid, integer object keys)

> **In short:** `Passability` now keeps every tile's move cost and its passable/door flags in
> packed arrays. The arrays are refreshed from `TileGrid.mark_dirty()`, the hook every tile and
> object change already calls. So `passability()` no longer formats a key, and the route cost
> callables, regions and rooms read integers without allocating. `ObjectTable` keys its maps
> by integer tile index. The `"%d_%d"` String key now exists only where the save and
> `state_hash()` are written, and their output is unchanged. `RegionMap` builds the whole map
> from row runs instead of a tile-by-tile flood. `RoomMap` skips the re-flood when a tile's
> open/door state did not change.
>
> Behaviour is unchanged. The A2 scenario dump is byte-identical to `main` (`89d44a0`):
> **0 of 14 files differ**. That covers saves, event logs, every `state_hash()`, region ids,
> rooms, `get_objects()`, a `passability()` sample, and the region ids of the generated
> seed-42 256×256 map. The save format is unchanged and there is no schema bump.
>
> Acceptance (`bench_route_search`, same host, `main` and branch run back to back):
> - region full build, generated map: **266.06 → 3.90 ms (target ≤ 50)** ✓
> - `rooms on_passability_changed`, no passability change: **106.42 → 0.04 ms (target ≤ 1)** ✓
> - µs/expansion on the generated map: **3.81 → 1.79 at d=256, 3.70 → 1.82 at d=128,
>   3.87 → 1.92 at d=64** ✓. **Not met for the two short searches:** d=32 is
>   4.06 → 2.13 and d=8 is 5.27 → 2.78. For a search that short the floor is
>   `RouteSearch`'s own per-search cost, not the map query. The same bench with a bare-array
>   cost callable, which does no map query at all, gives 3.28–3.90 µs at d=8 on both
>   branches. See "Known limitations".
>

## How the cache stays correct

- **Built lazily**, on the first query, like regions and rooms. `WorldState._init()` writes the
  generated map and berry bushes before any query: `_built` is still `false` after `new()`,
  checked with a probe.
- **Refreshed at the existing mutation points.** Every core write of a tile kind or an object
  already calls `TileGrid.mark_dirty()`: `ToilBindings._toil_on_work_complete()` (the only core
  writer of `tiles[]`, per `grep "tiles\[" game/scripts/core`) and every touched footprint
  tile in `ObjectTable.set_object()`. `mark_dirty()` now refreshes that tile.
- **Dropped on wholesale replacement:** `TileGrid.decode()`, `ObjectTable.decode()` and
  `place_generated()` call `reset_cells()`.
- **Self-checking against direct `tiles[]` writes.** Each tile remembers the tile kind it was
  computed from (`_kind`). A query recomputes a tile whose `TileGrid.tiles` entry differs.
  `passable_mask()`/`room_cell_flags()` first compare the whole array, one native `Array ==`.
  54 test files write `tiles[]` directly (about 360 sites), many of them in mid-test, and the first suite run without
  this check failed `test_rescue` and `test_dig_find_distribution` on stale tiles. This keeps
  them, and any future writer that forgets `mark_dirty()`, correct without touching ~360 test
  lines. A direct write to ObjectTable's maps after a query is not detected, and the class doc
  says to call `reset_cells()` there. The suite contains no such write other than the two
  fixtures adapted above.

## Identical region ids

The old build ran a flood-fill from each unlabelled passable tile in row-major scan order, so
region *k* is the one whose first tile in row-major order comes *k*-th. The new build labels
row runs (`PackedByteArray.find()`), unions runs that share a column with a run in the row
above (4-connectivity), and gives each set the next id the first time one of its runs is met
in run order. Runs are created in row-major order, so the first run met of each region holds
that region's first tile. Same ids, same `_next_id`. Split and merge keep their statements and
neighbour order: the first neighbour keeps the old id, and later unconnected neighbours take
fresh ids in up/left/right/down order. Only the visited/frontier containers changed.
Evidence: `regions.json` (all 65,536 ids of the generated seed-42 256×256 map) and the 48×48
id array in every trace line are byte-identical to `main`. `test_regions` and `test_rooms`
pass.

## Rooms without a re-flood

A room's shape depends only on which tiles are open (passable and not a door) and which are
doors. When `on_passability_changed(x, y)` finds `(x, y)`'s open/door state unchanged
(soil → plowed_soil, a bed placed or removed), a rebuild would recompute the same members,
doors and `enclosed` flag. The only thing that can differ is `has_bed`, and only through
`(x, y)` itself, so the fast path adds or removes `(x, y)` in that room's bed set. A changed
state takes the original path: neighbourhood ids before and after, clear, rebuild. The test
`test_rooms` "placing a bed on an interior tile must set has_bed true even though passability
never changed" covers the bed case and passes. The dump's room probes (a walled 5×5 room,
door removed at tick 260 and restored at tick 300, a bed inside) are identical to `main`.

## Contract impact and hash coverage

- **Contracts, schemas, ADRs:** none changed. The passability rule, door semantics, region
  and room definitions and every public signature (`passability(x, y, faction)` still returns
  `{passable, cost, is_door}`) are the same. No new toil, job giver or decision layer, so no ADR.
- **Save format:** unchanged. `ObjectTable.encode()` hands `StateCodec._encode_objects()` the
  same String-keyed maps, and `state_codec.gd` is untouched. Saves are byte-identical (dump).
- **`state_hash()` coverage:** still hashed: `objects` and `object_health`, re-keyed to the
  same `"%d_%d"` keys (`JSON.stringify` sorts keys, so the bytes are the same), plus `width`,
  `height` and `tiles`. Still not hashed: `object_factions`, `object_origin`,
  `object_orientation`, and every derived cache. That includes the new Passability arrays and
  RoomMap's `_cell_state` and bed sets, like regions, rooms and the water cache before them.

## Known limitations

- **µs/expansion ≤ 2 holds for the d ≥ 64 searches but not for d=8 (79 expansions) and d=32
  (1,728).** Those searches are short enough that `RouteSearch`'s per-search and per-resume
  costs dominate. Even with no map query at all (the open-grid array-cost rows) d=8 costs
  3.3–3.9 µs per expansion. The map-query part is now the same as the bare-array callable:
  on long searches the generated map runs at 1.8 µs against the open grid's 1.4 µs. Getting
  short searches under 2 µs would mean changing `routing/route_search.gd`, which is not an A2
  path. If the owner reads the acceptance line as "the long-distance rows" (the ~8 baseline it
  quotes matches A0's d=64–256 rows, 8.1–8.9 µs), it is met.
- A direct write to `ObjectTable`'s maps after a passability query is not detected by the
  cache (tile writes are). Core never does this; a test fixture must call
  `TileGrid.reset_cells()`, as the two adapted fixtures do.
- The regions split (block one tile in a large open region) still floods the old region once.
  It is faster (packed containers) but not the incremental algorithm. Not an A2 acceptance
  line.
- Rooms' full build (first `get_rooms()`) still floods every area, now around 368.52 ms on
  the generated map. Not an A2 acceptance line; A19 deals with the region side of tick 1.
