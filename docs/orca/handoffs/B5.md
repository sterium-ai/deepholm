# B5 handoff: saves refused mid-rescue, ground berries unhashed and losing their faction

> **In short:** Three persistence bugs found by the R2/R4 probes, all present on `main`, are fixed.
> (1) A save taken while a rescue was mid-work was refused: the owner of the rescue's work
> timer was written with a garbage tile (`{x: 0, y: 12044}`). Owners are now saved as explicit
> records (tile + job scope), built and read through one key codec in `WorkProgress`.
> (2) `state_hash()` now covers ground berries. (3) Ground-berry factions are saved and restored.
> Save schema 26 → 27, with a migration, a v26 fixture and ADR 045. Over 1,600 ticks of the
> R2/R4 scenarios, saved and reloaded after every tick, refused saves dropped from 197 to 0 and
> ticks with lost berry factions from 1,019 to 0.

## The fixes

1. **Save refused.** The owner encoder used to split a key like `"job_120:44_33"` on `_`, which gave
   `{x: 0, y: 12044}`. `SaveIO.write_atomic()` then refused the save with `schema_error: invalid
   tile coordinates` (R4 diagnosis, `handoffs/R4.md`). Now both work-progress arrays describe a
   key the same way, `target` + optional `ownerJobId` (the scope), and owner entries keep `jobId`
   for the owner. Encoding and decoding go through `WorkProgress.key_parts()` and `key_of()`, so
   the codec never parses a key by hand. On load the persisted owner record matches the progress
   key again. Before, the scoped owner was silently lost and only recovered by the
   execution-state fallback (`reconstruct_owners()`). The new test proves the record alone
   restores it.
2. **Berries hashed.** `ItemTable.hash_into()` adds `ground_berries`. `JSON.stringify` sorts keys,
   so a loaded world with a different insertion order hashes the same; the probe confirms it.
3. **Berry factions persisted.** Each `groundBerries` entry has a `factionId`, restored into
   `ground_berries_factions`. The migration backfills `"colony"`, the only value
   `spawn_berries_item()` has ever written.

## Contract impact

- **Save format changed → schema bump 26 → 27**, migration `_migrate_v26_to_v27()`, inline v26
  fixture in `test_save_migration.gd`, schema JSON and `save-system.md` updated, ADR 045.
  - `groundBerries`: `[{target, berries}]` → `[{target, berries, factionId}]` (required).
  - `workProgressOwners`: `[{target, jobId}]` → `[{target, jobId, ownerJobId?}]`. A plain-tile
    owner encodes exactly as before (the v26 fixture test checks the re-encode). `workProgress`
    is unchanged.
  - v26 files need no owner rewrite: a scoped owner made every v26 write fail, so only plain-tile
    owners reached disk.
- **`state_hash()` coverage** for these modules:
  - `ItemTable`: included `items`, `next_item_id`, `dig_find_rng`, **`ground_berries` (new)**.
    Deliberately excluded: `item_factions`, `ground_berries_factions` (decide nothing in a tick;
    same rule as item factions), `pending_dig_finds` (empty between ticks).
  - `WorkProgress`: unchanged. Included `suspended_work_progress`; excluded `progress` and `owners`.
- Old fixtures (v1–v25, files and inline) still migrate through the whole chain and load:
  `test_save_migration: PASS`.

## Review round 1

Verdict `REQUEST_CHANGES`, one blocking finding, no non-blocking ones:

> `save_migrations.gd` — the v26 guard never validates `groundBerries`: an integrity-valid save
> containing `[null]` reaches an invalid dictionary dereference, while `{}` silently becomes `[]`.

Confirmed and fixed. `_is_schema_v26_state()` now returns false unless `groundBerries` passes
the file's existing `_has_dictionary_entries()` (an array whose every entry is a Dictionary).
Entry *contents* still go through `SaveIO._validate_state()` after migration, as for every other
step. New checks in `test_save_migration.gd`:
`_check_malformed_v26_ground_berries_is_rejected()` (six malformed values, in memory) and
`_check_malformed_v26_ground_berries_rejected_through_save_io()` (`[null]` and `{}` in real
integrity-valid files). With the guard line disabled, the first prints
`SCRIPT ERROR: Invalid cast: could not convert value to 'Dictionary'` and the `{}` case returns
`ok: true` with `groundBerries: []`, so both checks fail; with it, `test_save_migration: PASS`.
While there: the v26 fixture dir was not removed at the end of the test; it now is.

## Known limitations

- **Pre-existing hash mismatch after load, around incidents (not fixed; outside B5).** In the
  probe, a world reloaded during the first ticks after `trader_visit`/`wolf_attack` does not hash
  equal to the live one. Diagnosis at r4 tick 62 (wolf attack submitted at 60): `to_save_state()`
  and the reloaded `to_save_state()` differ only in `jobs` and `scheduling`. Job `job_16`
  (`kind: incident`, `status: queued`) comes back `status: cancelled`,
  `reason: cancelled_by_command`. The load-time incident reconcile in `StateCodec.decode()`
  cancels a still-queued incident job. The same ticks fail on `main` (42 before, 42 after). This
  is incident/job persistence, which B5's non-goals exclude ("anything else in persistence"). It
  needs its own `B*` task: "a save taken while an incident job is still queued loses the job".
  The B5 probe lists those ticks but does not fail on them.
- **Shared `user://`.** Concurrent Godot processes (other worktrees) can make `SaveIO` tests fail
  with `rename_failed`. That is what happened to the 4 baseline failures; the final run had none.
- **Stale comment outside the owned paths:** `world_state.gd:696-698` lists each module's hash
  keys and does not name `ground_berries`. The authoritative list is `ItemTable`'s class doc
  (updated). Left for R16 (comment pass) or the next `world_state.gd` owner.
- **Replays** recorded before this change have different `state_hash()` values wherever berries
  lay on the ground (ADR 045, Consequences).
