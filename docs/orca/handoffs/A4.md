## What changed, and why the behaviour is the same

### Need sources

**Before:**
- Each colonist that started a search called `need_source_candidates(kind)`.
- That call ran `_reachable_candidates_only()`: for each source, `colonists.any(reachable(colonist, source))`.
- So one tick cost sources × colonists² region checks: 2218 water tiles × 100 × 100 in the bench.

**Now:**
- `need_source_candidates(kind)` collects the colonists' region ids once (dropping 0).
- It keeps a source when one of the regions that `RegionMap.reachable()` admits for it is in that set:
  - a passable source belongs to its own region;
  - an impassable one (water) belongs to the nonzero regions of its 4 orthogonal neighbours;
  - out of bounds is never reachable.
- This is `reachable()`'s own rule rewritten per source, so the kept list is the same list in
  the same order. With no colonists the unfiltered list comes back, as before.
- NeedGiver calls it once per kind per `advance()`. Nothing inside `advance()` changes a
  source, a region or a colonist's tile:
  - `interrupt_current_job()`/`resume_interrupted_job()` only pause or resume work;
  - `_commit()` only queues a job.

**Deviation from the goal's wording, stated openly:** the goal says "a colonist's candidates
are a lookup by its own region id". I built exactly that first, and `test_combat`
(`_check_need_search_survives_flee_activation`) failed:
- Before A4, every colonist gets *every source some colonist can reach*. That includes sources
  only another actor reaches.
- That test walls a worker in and puts water outside, reachable only by a far-away raider.
- It relies on the worker's search staying alive over those sources for several ticks.
- With a per-region lookup the worker gets an empty list and fails at once, which is a
  behaviour change.

So every colonist still gets the same list. The region ids only make that list cheap, and
it is built once per pass. The cost goes from O(sources × colonists²) per tick to
O(sources × 4 + colonists) per kind per pass, plus the existing per-colonist sort.

### Actor index and trust model

Actors are mutable Dictionaries that many places write directly: tests (`_colonists`
appends, x/y writes) and the viewer's debug scenario. An always-on index would go stale on
those writes. So:

- **Inside `tick()`** (`begin_tick()` … `end_tick()`), the index is rebuilt from the roster in
  O(n) at the start and trusted. Every in-tick roster or position change goes through a hook:
  - `_append_colonist()` → `added()`;
  - `_remove_colonist_by_id()` → `removed()`;
  - `ToilExecutor.advance_route_step()` and TrenchSystem's rescue and escape → `moved()`;
  - `NeedsSystem.ensure_needs()` → `replaced()`, because it rebuilds an incomplete actor as a
    *new* Dictionary in the roster slot.

  A grep for `["x"] =`, `["y"] =`, `colonists[…] =` and roster `append`/`remove` in
  `game/scripts/core` finds no other writer, re-checked on `7abae43`:

  ```powershell
  rg -n '\["x"\] = |\["y"\] = |colonists\[[^]]+\] = |_colonists\.(append|remove_at|erase|insert|clear)' game/scripts/core
  ```
- **Outside a tick** (commands, viewer reads, tests between ticks), `find()` and `any_at()` run
  the same linear loop as before. Out-of-tick results are identical to `main` by construction.
- **A roster that repeats an id** leaves the index untrusted for that tick, so it falls back
  to linear lookups.
- **Order inside a tile does not matter.** `any_at()` is a boolean, and targeting picks the
  hostile occupant by smallest id.

The first full-suite run on the rebased head caught the missing `replaced()` hook.
`test_tool_items`, `test_toils_dig_chop_regression` and `test_architecture_rules` failed,
because `ensure_needs()` had swapped `colonist_0` for a rebuilt Dictionary inside the tick and
`_find_colonist()` returned the stale one. The hook was added, `test_actor_index` now checks
it inside a real tick, and all three pass.

`ItemTable._ids_at` follows the same model. In production every in-tick item write goes
through `_place_ground_item()`/`_remove_ground_item()`. The out-of-band writers are the
viewer's `debug_scenario.gd` (through `world._items`) and 26 test files, and they act between
ticks.

### Combat

`nearest_adjacent_hostile()` used to build a position map of every actor on every call. That
was O(n) per attacker, so O(n²) per tick in `resolve_tick()` and again in
`ApproachGiver.advance()`. Each pass now builds `actors_by_tile()` once:
- **Nothing moves during either pass.** No toil runs there.
- **Nothing is removed during either pass.** `resolve_tick()` only reports deaths to its
  caller, and cancelling an approach job despawns nobody.
- **Deaths during `resolve_tick()`:** the old per-call rebuild skipped a victim killed earlier
  in the same pass. The lookup now does the same: `_pick_hostile_occupant()` checks `dead`.
- **"Has a health component"** cannot change mid-pass, so the map filters on it once.
- **`other == actor`:** the attacker is never on its own neighbour tile, so excluding itself
  needs no check.

The 8-offset scan order and the smallest-id tie-break are unchanged. The combat index is a
per-pass map rather than `ActorIndex`, because `resolve_tick()` is called from
`actors/combat_system.gd`, which is outside the owned paths.

### Tick 1 with 10 colonists: why ≤ 100 ms is not met

[`A4-first_tick_split.gd`](A4-first_tick_split.gd) builds the bench's own world
(`BenchCommon.world_with_colonists(42, 256, 256, n)`, water 20). It times the one-time pieces
separately before tick 1:

```

first_tick_split: actors=25 regions=269.0ms water_cache=8.2ms candidates=6.5ms rest_of_tick1=29.9ms
first_tick_split: actors=100 regions=265.6ms water_cache=8.3ms candidates=7.2ms rest_of_tick1=105.3ms
```

(These are from the final HEAD. The first `actors=10` line, 295.4 ms for regions, is a warm-up
run of the same case.)

```powershell

```

The lazy full-map `RegionMap` build (`TileGrid.get_regions()`, a flood fill of 256×256 in
`map/regions.gd`) costs about 260–295 ms, whatever the colonist count. A4's own part of the
10-colonist tick 1 (water cache, candidate pass, rest of the tick) is about 31 ms. The bench
header already says tick 1 "pays the lazy full-map region build". `map/regions.gd` is not an
A4 owned path, and the owner decided not to widen the scope. The new backlog entry **A19**
(`todo`, parallel-safe) targets that build, aiming at tick 1 ≤ 100 ms for 10 colonists.
