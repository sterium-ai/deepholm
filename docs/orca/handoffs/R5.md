# R5 handoff: extract `ConstructionSystem`

> **In short:** `game/scripts/core/objects/construction_system.gd` (`ConstructionSystem`) now
> owns the construction sites (`ConstructionSiteTable`), the two site-fetch runtime caches and
> the whole construction flow: build/build_line submission and their read-only checks, the
> footprint/terrain checks, site fetch source selection, site work progress, finalize, cancel
> and the enclosure check. `WorldState` delegates, and `ConstructionGiver` is now wired only to
> `ConstructionSystem` and sibling modules, never to `WorldState`. Behaviour is unchanged. A
> construction-heavy scenario with seven mid-build save/load round trips produces the same
> saves, events, per-5-tick site trace and `state_hash()`, byte for byte, as `main`, and so do
> the R1–R4 probes. `world_state.gd` drops from 3973 to 3264 lines.

**Move, not rewrite.** [`R5-move_check.py`](R5-move_check.py) takes each of the 29 moved
functions from `main`'s `world_state.gd` and applies the listed mechanical renames. It then
compares the result with the body in `construction_system.gd`, statement by statement, with
comment and blank lines dropped. The renames are:

- the new names;
- `_sites` → `site_table`, `_site_fetch_source_retargeted` → `site_fetch_source_retargeted`;
- `get_object(`/`get_tile(`/`passability(` → `_object_table.`/`_tile_grid.`/`_passability.`
  (the `WorldState` methods were one-line delegations to exactly these);
- `_colonist_at`, `_find_job_colonist`, `_finish_job`, `_drop_carried_haul_item`, `_route_cost`
  → injected `Callable`s (`.call(`), with an explicit type on the two `var x := …` lines
  that assigned their result (`var colonist: Dictionary =`, `var cost: int =`), because GDScript
  cannot infer a type from `Callable.call()`;
- `in _colonists:` → `in _get_colonists.call():`.

Result: `move_check: 29 function(s), 0 differ`. The three new helpers (`site_work_ticks_remaining`,
`add_site_work`, the persistence trio) contain the removed statements in their original order.
The diff of `world_state.gd` shows each call site.

**Dependencies (no back-reference).** `ConstructionSystem.new(object_definitions, tile_grid,
passability, object_table, zone_table, item_table, scheduler, event_log, get_colonists,
colonist_at, find_job_colonist, finish_job, drop_carried_haul_item, route_cost)` is built in
`WorldState._init()` right after `WorkProgress`, before `ToilExecutor` (which takes its
`construction_site_exists`/`construction_site_deposit`) and before `ConstructionGiver`. Its
arguments are:

- sibling modules, which `StateCodec.decode()` restores in place and never reassigns;
- the shared `_object_definitions` dictionary;
- a lambda returning `_colonists`, because `decode()` reassigns that field;
- five bound `WorldState` methods as `Callable`s.

It never stores or receives `WorldState`. The reservation table is fetched through
`_scheduler.queue.get_reservation_table()` on every call, as before (`queue.restore()` replaces
it).

**`ConstructionGiver` no longer talks to `WorldState`.** Its nine callables are now
`_construction.site_table.list`, `_scheduler.queue.get_jobs`, `_item_table.get_items`,
`_zone_table.is_in_any_zone`, `_construction.construction_item_reservation_owner`,
`_construction.submit_site_fetch`, `_construction.submit_site_work` and
`_construction.site_table.materials_met`/`remaining`.

Two of them used to be `WorldState` methods:

- `get_items` was `WorldState.get_items()`, a one-line delegation to `ItemTable.get_items()`.
- `get_jobs` was `WorldState.get_jobs()`, which is `JobQueue.get_jobs()` plus
  `ToolHandover.apply()` on each copy.

That overlay only rewrites an active job that is waiting for a tool handover
(`ToolDropToil.waiting_for_handover()` needs a tool reserved by that job). `site_fetch` and
`site_work` declare no `needs_tool` in `content/jobs.json`, and they are the only kinds the
giver reads, so it sees the same records. The identical scenario trace below confirms this.
`construction_giver.gd` itself changes only in doc comments.

**Kept in `WorldState` on purpose** (other tasks own them; receiver renames only):

- every `_toil_*` hook (R11): `_toil_go_to_skip_assignment_path`, `_toil_site_id_for`,
  `_toil_pick_up_count_for`, `_toil_on_pick_up_success`, `_toil_on_deposit_success` and the
  `site_work` arm of `_toil_on_work_complete`;
- `_resolve_giver_association()`, which calls `_construction.release_site_builder()`;
- `_route_cost()` and `_UNREACHABLE_ROUTE_COST`: a routing helper, not in the R5 list, used by
  `_toil_on_pick_up_success()` and injected into the module;
- the command handlers outside the R5 list (R10): `_check_cancel_site_command()`,
  `_apply_cancel_site_command()`, `_apply_cancel_job_command()`, `_check_place_object_command()`.
  `preview()`/`apply()` dispatch build/build_line to the module.
- `_finish_job()` still erases both caches, now on `_construction`.

## Contract impact

- No schema bump, migration, ADR or contract change.
- **Save format:** unchanged. `constructionSites` = `[{id, kind, origin {x,y}, orientation,
  requiredMaterials, heldMaterials, progress, buildTicks, maxBuilders, builderIds}]` sorted by
  site id, at the same key position, optional on load. The next site id is still re-derived
  from the highest `site_<N>`. The 8 `save_*.json` and `states.json` below are byte-identical.
- **`state_hash()` coverage** (`R5-hash_coverage.gd`; `main` and the branch print the same 6
  lines):
  - Included (unchanged): `construction_sites` (held materials, progress, builder ids, site
    presence), now written by `ConstructionSystem.hash_into()` with the same key and value.
  - Deliberately excluded (unchanged): `site_fetch_source_retargeted` and
    `site_fetch_picked_kind` (runtime caches, never saved).
- **Invariants from trimmed comments** are in the `ConstructionSystem` class doc:
  - a site exists from acceptance, before any material, and reserves its footprint under
    `owner_key(id)`, never a job id; finalize and cancel release it;
  - build and build_line share one footprint rule and reason;
  - build_line canonicalizes and de-duplicates its tiles, skips overlapping footprints and runs
    the enclosure check once before creating anything;
  - the fetch source chosen at submission is a seed that is swapped on activation;
  - `site_table.progress` is the only work counter (`site_work` never writes `WorkProgress`);
  - both caches are erased on termination and never saved or hashed;
  - `constructionSites` is persisted and hashed, and the next id is re-derived.

  Each function keeps a 1–4 line *why*. The per-component enclosure baseline (build_line tiles
  may span unconnected areas) is in `_would_enclose_tiles()`'s doc and is covered by
  `test_wall_orders`' `_check_batch_with_a_disconnected_unreachable_candidate_still_detects_enclosure`.

### Byte identity

[`R5-scenario_dump.gd`](R5-scenario_dump.gd) uses seed 777, a 48x48 map, 10 colonists and
incidents on. It sets up:

- a 5x5 stockpile with 25 small wood/stone stacks, so fetch jobs hop between sources and chain
  onto sibling sites;
- two workbenches (2x1, two builders, two materials), walls, a bed, a door and a stone wall;
- three build_line rows: one shuffled, with a duplicate and the colonist's own tile; one of
  overlapping workbenches; one vertical;
- a corner pocket plus a build_line and a single wall that would seal it (both rejected);
- `cancel_site` at tick 180 and `cancel_job` with a site id at tick 330;
- chops, and three random build/build_line/cancel_site/workbench commands every 20 ticks.

`SaveIO`), reloaded with `from_save_state()`, and play continues on the reloaded copy. Every 5
ticks the probe traces the raw site records, the public view, both caches, the site jobs and
`state_hash()`.
