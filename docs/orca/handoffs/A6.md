# A6 handoff: bounded event and dirty-cell streams

> **In short:** The world event log, JobQueue's event log and the dirty-cell log now keep a
> bounded window: 8,192, 4,096 and 4,096 entries. They can also be read through a cursor:
> `WorldState.get_events_since(sequence, types)` and `get_dirty_cells_since(cursor)` return only
> what is new since that cursor, plus `next` and a `truncated` flag. The viewer (`map_view`,
> `status_text`, `work_table_panel`) reads only what is new instead of deep-copying the whole
> log on every refresh. `map_view` does one full rebuild when a read comes back truncated.
> Events are still not saved, and the save format is unchanged. The R1 scenario's events,
> saves and results are byte-identical to `main`. Suite on the rebased head:
> `run_tests: all 101 test(s) PASS  [845s]` (`main` has 100 test files; the one added here is
> `test_event_streams.gd`).

## Design notes the reviewer should check

- **Cursor = event sequence.** `next` is the next sequence `EventLog` will draw. A read returns
  the retained events with `sequence >= cursor`, in log order. Log order is (tick, priority,
  entity, sequence), not append order. So a later read can return an event that sorts *before*
  one an earlier read returned: a command applied at tick T sorts before tick T's
  `tick_advanced`, which was already read. The reads merged in log order are the log. The test
  pins this, and `status_text` merges with `bsearch_custom` to keep the old order.
- **Where each log trims.** `EventLog` trims on insert, with hysteresis. `JobEventLog` trims only
  at the start of `JobQueue.tick()`, never in the middle of a command. So a burst (a 2,000-tile
  area order) is held whole until `collect_queue_events()` copies it. Every command handler and
  every `WorldState.tick()` collects. `TileGrid` trims on `mark_dirty()`.
- **`truncated`** is true when retention has already dropped an entry at or after the cursor.
  `map_view` answers with a full rebuild. `status_text` and `work_table_panel` keep what they
  already read: incident lines and the latest alert outlive their events.
- **Persistence and hash.** Only `eventSequence`/`queueEventSequence` were persisted, and that is
  unchanged. `_trimmed_sequence`, `_arrival` and `dirty_base` are not saved: they start empty or
  zero, exactly like the event list. None of the event or dirty state is in `state_hash()`,
  before or after. This is why the R1 saves and hashes are identical.

## Known limitations

- `JobEventLog` trims by count at `tick()`. If more than 3,072 queue events were emitted since
  the last `collect_queue_events()`, the oldest uncollected ones would be lost from the world
  log. That cannot happen today: every command handler collects before returning, and
  `WorldState.tick()` collects every tick. A future emitter that skips both would need to
  collect.
- `status_text`'s incident state is static and remembers one world (by instance id). That
  matches its single caller (`boot.gd`'s one label). Two worlds rendered in alternation would
  restart the state on every switch.
- A cursor reader only sees events whose sequence comes from `next_sequence()`. Every core path
  does this. A hand-made event with a lower sequence is invisible to a reader already past it;
  `test_work_table_panel.gd`'s helper was fixed for this reason.

  banners unchanged).
