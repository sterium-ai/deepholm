## What changed, and why the order is the same

**Before:** the frontier was an `Array` in insertion order. `_pop_min_index()` scanned all of
it for the lowest `_cost`, taking the earliest index on ties, then called `remove_at()`. On top
of that, every expansion allocated a 4-element array and sorted it with a lambda.

**Now:** the frontier pops by (accumulated cost, insertion number).
- `_cost_heap` is a binary min-heap of the distinct costs still waiting.
- `_buckets[cost]` is a FIFO of the tiles at that cost.
- The insertion number (`_next_seq`) only grows, so each FIFO is already in insertion order.
  Its head is the same "lowest cost, earliest insertion" tile the scan picked.
- A tile's cost is fixed when it is discovered, as before (it is marked visited then), so keys
  never change.
- The neighbor order `(0,-1), (-1,0), (1,0), (0,1)` is the row-major order the lambda sort
  always produced.

Other details:
- **Neighbor checks:** done in the same order as before: visited, bounds, cost.
- **Visited set:** now `_start` plus the keys of `_came_from`, the same set in the same
  insertion order.
- **`snapshot()`:**
  - `"visited"` is rebuilt from `_came_from`;
  - `"frontier"` merges the FIFOs back by insertion number, so it equals the old array;
  - `_seeded` keeps `"visited"` empty for a search that ended in `_init()` (blocked start,
    or start == target), as before.
- **`restore()`:**
  - rebuilds the costs from `came_from` with the current `cost_fn`, as before (the A7 defect is
    unchanged and out of scope);
  - re-pushes the frontier in its saved order, so the relative insertion order is kept.

**Deviation from the literal goal, stated openly:** the backlog says "a binary heap keyed by
(cost, insertion order)". I first wrote exactly that: one heap entry per frontier tile,
compared by cost and then insertion number (not in the diff). It passed the recorded test but
measured 74–76 ms for open d=256 on this machine, which misses the 60 ms target,
because the sift-down over ~9 levels in GDScript dominated. The version in the diff keeps
the binary heap but over distinct costs only. The FIFO gives the insertion-order tie-break,
which yields the same order with O(1) pops between cost changes. It reached 47–50 ms.

**"No per-step allocation":** the per-expansion array and lambda sort are gone. What remains
per step:
- the `_came_from` insert (the search state itself);
- an amortised append to a FIFO;
- one small `Bucket` object per *distinct* cost value (not per step).

**Re-route snapshots:** while a re-route is live, `route.rerouting` used to hold a full
`snapshot()` (frontier, visited, came_from), rebuilt every tick. It now holds `summary()`:
`start`, `target`, `status`, `expansions`, `resume_calls`. Every in-memory reader only uses
those keys:
- `ToolDropToil`/`ToolFetchToil` read `["target"]`;
- the viewer and `colonist_panel.gd` check `!= null`;
- tests read `status` and `resume_calls`.

`StateCodec._encode_route_field()` now writes `world._reroutes[id].snapshot()` at encode time.
If no live search exists, it falls back to the stored value, as before. The pending searches
in `GlobalAssignment` and the givers were not touched.

## Contract impact

- **Save format: unchanged.** No schema bump. Key names, nesting and value shapes are
  identical, shown byte for byte by the probe below. No migration or fixture needed.
- **`RouteSearch` API:** adds `summary()` and `NEIGHBOR_OFFSETS`, and removes the private
  `_ordered_neighbors()`, `_pop_min_index()`, `_visited`, `_frontier` and `_cost`. Nothing
  outside the module used them (checked with grep) except `MeasuredRoute`, which is updated.
- **`state_hash()` coverage: unchanged.** `state_hash()` hashes the colonists through
  `StateCodec._hash_colonists()`, which puts each live re-route's full `snapshot()` where the
  in-memory summary sits. The hashed value is the same Dictionary `main` stored on
  `route.rerouting`, so every `state_hash()` value is identical to `main`'s (probe below). The
  full snapshot is now built at hash time rather than every tick. When no colonist is
  re-routing, the colonists array is hashed directly, with no copy.
- **No ADR:** paths and behaviour do not change. The backlog does not ask for one.
- **Budgets:** none raised. `toil_executor.gd` is at 960 lines against its cap of 970, and
  `world_state.gd` stays at 2871, the same as `main` `d2bdd30`, against its cap of 2880.

### Save byte-identity mid-re-route (snapshot moved to encode time)

[`A3-reroute_save_dump.gd`](A3-reroute_save_dump.gd) sets up the following scenario:
- seed 7, 64×64 all-soil map;
- 3 colonists in the north-west corner, with dig orders and picks in the south-east;

  spans many ticks;
- wall rows dropped across the map at ticks 20 and 45.

reloads from its own save every 25 ticks.

- `saves.json` (17,757,599 bytes, 45 encodings holding 131 in-flight `"searching"` re-route
