## Observer hook (scope extension: `world_state.gd`, `boot.gd`)

**Why outside the owned paths.** The viewer modules (`map_view`, `order_input`,
`colonist_panel`, `work_table_panel`, `debug_scenario`, …) call `world.apply()` directly, so a
live session cannot be captured from the owned paths alone. I asked in the terminal. The owner
chose an optional command observer in `WorldState.apply()` (1–3 lines) plus the hookup and a key
in `boot.gd`, built on R12's façade once R12 was in `main`. R12 was not in `main` for the first
handoff or review rounds 1–3. The owner then wrote that R12 is in `origin/main` (`63d3d5f`) and
asked for the hook, approving `world_state.gd`, `boot.gd` and `tools/replay.gd` as scope
extensions.

**What changed.**

```gdscript
var command_observer: Callable # optional (command, result) listener after each apply() from outside the core (area-order expansion bypasses it); never mutates (A11)
func apply(command) -> Dictionary:
	var result := _commands.apply(command); if command_observer.is_valid(): command_observer.call(command, result)
	return result
```

When nothing is recording, this costs one `is_valid()` per command; nothing else changes.
`CommandRecorder.start()` sets the observer to `observe_command.bind(world)` and `stop()`
clears it, so `boot.gd` only calls `start()`, `stop()` and `observe_tick()`. The viewer purity
rule in `test_architecture_rules` still passes: the recorder assigns a property and calls no
world method other than `get_*`.

**The bug the hook exposed.** On the R12 base, `test_command_replay` passed before the hook (I
checked it in a separate worktree at the pre-hook commit). With the first version of the hook
it diverged at checkpoint 151, one tick after the test's tick-150 `area_order` dig. The cause:
`AreaOrders` was built with the public `apply`, and it calls that once per tile while expanding
inside `tick()`. The observer therefore recorded every expanded `dig`, and the replay applied
each one twice, once from the log and once from its own expansion. The fix is the one changed
`AreaOrders` line above: the expansion calls the router directly. The behaviour is the same as
before the hook, because `apply` was exactly `_commands.apply`. Only commands from outside the
core are observed. `grep` shows `AreaOrders` is the only core module that receives `apply`.
`test_boot_command_recording` checks for this: with the old line put back temporarily, it fails
four times with "an area order's expanded per-tile dig must not be recorded".

**`boot.gd`.** F9 starts recording on the running world from its current tick, and F9 again
stops it and writes `user://replays/replay-<seed>-t<start>-<end>-<date>.json`. The wall clock
only names the file, in the viewer. `_on_ticked()` calls `observe_tick()` before the autosave
check, so the checkpoint is the state right after `tick()`, as the replay expects.
`_replace_world()` (New Game, Load, Debug scenario) stops and saves first, so a recording never
spans two worlds and the replaced world keeps no observer.

## Design

- **Start state, not just the seed.** `build_default_world()` places its starting items
  outside `apply()`, and a recording may begin on a resumed save or mid-session. So the log
  keeps `to_save_state()` at the start tick. The replay rebuilds with `from_save_state()` and
  then `enable_incidents()`, the same thing `boot.gd` does on Load. The seed, content version
  and generator version are kept beside it. A content or generator version that differs from
  the running build is refused with a typed code.
- **Checkpoint semantics.** Checkpoint *T* is `state_hash()` right after the `tick()` that
  reached *T*, before tick *T*'s commands. The first checkpoint is the start tick; then every
  `checkpointInterval` ticks (default 10). There is also a final hash after the last tick's
  commands. A divergence reports `tick` (the first checkpoint that differs) and
  `last_matching_tick`, so the cause lies in the ticks after the last match, up to and including
  the reported tick.
- **Rejected commands are recorded too**, with their `ok`. Some rejections still advance the
  JobQueue sequence (`commands/README.md`). Replay also reports a `command_result` divergence
  when a command that was accepted is now rejected, or the other way round.
- **Observed commands are the external ones.** Only commands from outside the core are
  recorded; area-order expansion inside `tick()` bypasses the observer (see "Observer hook").
  This is what makes "apply the recorded commands, then `tick()`" reproduce the session.
- **Boundary.** `test_architecture_rules` allows viewer scripts to call only `get_*`,
  `apply()`, `get_events()` and `tick()` on a world. So everything that hashes, snapshots or
  replays lives in core (`ReplayLog`). The viewer module only routes calls to it and owns the
  file, the same split as `SaveWiring`/`SaveManager`. `ReplayLog` takes the world as a
  parameter and never stores it.
- **File.** JSON. `initialState` is a base64 Variant blob, because the save state carries
  64-bit RNG states that a JSON double would corrupt. The seed is a string. Each command
  is stored as `JSON.from_native()`, so an int stays an int and a float stays a float (review
  round 1). `validate()` refuses a log whose checkpoints are not exactly the recorded grid.
  The format is documented in `docs/architecture/replay.md`.

## Known limitations

- **One observer slot.** `command_observer` holds a single `Callable`. Only one recorder can
  listen at a time, which is all the viewer needs.
- After a world swap, the "Recording saved: …" status line is quickly replaced by the New
  Game, Load or Debug scenario status. The path is still printed to stdout and kept in
  `boot.last_recording_path`.
- A recording started while a trader offer is open does not carry it, because offers are never
  persisted. A later `accept_trade` then replays as a `command_result` divergence. This is
  documented in `replay.md`.
- A file is about 1.1 MB on the default map, almost all of it the start-state blob.
- `state_hash()` runs `ensure_*` normalisers. Checkpoints call it at the same points on both
  sides, so a replay is consistent with its own recording. Calls the live game makes elsewhere
  (autosave, boot hash) are not replayed. I did not prove those ensures idempotent. If one of
  those extra calls ever changed state, the replay would report it as a divergence; it would
  not pass silently.
- `test_command_replay` takes about 60 s: about 2,700 ticks of the full boot world with
  incidents on.
