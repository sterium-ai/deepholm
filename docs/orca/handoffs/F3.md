## Review round 2 (REQUEST_CHANGES) and fixes

- **Blocking: build XP was lost when a site completed its other builders.** When the
  builders' summed progress met `build_ticks`, `ConstructionSystem._finalize_construction_site()`
  finished the other builders with `_finish_job` directly. With two builders, that happens on
  a tick that is neither builder's own last tick, so nobody earned build XP.
  - The owner approved `core/objects/construction_system.gd` as a scope extension (owner
    decision 4).
  - The fix adds an optional `complete_builder` Callable. `_finalize_construction_site()`
    calls it in place of `_finish_job(.., "complete_job")` for each other builder, and keeps
    the old call when the Callable is unset.
  - `ToilBindings._init()` sets it to `_complete_job`, which finishes the job and awards XP
    only if the finish is accepted. The builder whose own countdown completed the site is
    still awarded by its own `_complete_job()`, so each builder job earns exactly once.
  - `world_state.gd` is unchanged.
  - New regression test `test_skills._check_every_builder_earns_build_xp_once`. It runs the
    real `build` command, ticks, stockpile delivery and `site_fetch` work, with
    `by_kind {"site_fetch": 0, "site_work": 5}`. Both a lone builder on a wooden wall and both
    builders on a workbench must end at exactly 5 build XP; 10 would mean a double award.
  - With the hook disconnected, the workbench builders end at 0 XP and `test_skills` fails;
    this was run and observed.
- **Blocking: wrong `site_work` claim.** The report and ADR 062 said `site_work` lasts 1 tick
  and earns XP per building tick. Both are corrected: the duration comes from the site, and
  XP is once per builder per site. The construction XP evidence is the test above.

  (Validation below).

## Design → implementation

| Design line (owner, 2026-10-30) | Implementation |
| --- | --- |
| Skill level 0–10 per labour | `colonist["skills"] = {labour: {level, xp}}` for the 7 worker labours. `core/actors/components/skills.gd` (`ActorSkills`), rules in `content/skills.json` (top level = `xp_to_next.size()` = 10) |
| XP per completed job, amount per job kind in content, default 1 | `skills.json` `xp_per_job: {default: 1, by_kind: {}}`. `ToilBindings._complete_job()` (all 4 toil-driven completions) awards `ToilExecutor.award_job_xp()` once `finish(complete_job)` returns ok |
| Level thresholds grow (content table) | `xp_to_next: [10, 25, 45, 70, 100, 135, 175, 220, 270, 325]`: XP from level L to L+1; `xp` restarts at 0 on a level up (remainder carries over) |
| Work speed linear 70 % (L0) → 160 % (L10), applied to `work_ticks` | `ToilExecutor.start_work()`: `max(1, roundi(work_ticks * 100 / speed))`, `speed = 70 + floor(90 * level / 10)`. Chop (40): 57 ticks at L0, 28 at L8 |
| Haul capacity +1 item every 5 levels | `ToilExecutor.hands_capacity()` = `HANDS_CAPACITY` (4) + `haul level / 5`, read by `pick_up` and by site-fetch's "hands full" rule (`toil_bindings.gd:284`); the save validator uses the same bound |
| Starting skills seeded: two labours at 3–6, the rest 0–2, from the world seed; a roster may fix them | `WorldSeeding._seed_skills()`: local RNG `placement_seed ^ 0x5C11` (never the simulation stream), two distinct majors drawn per colonist, then one level per labour. Roster entries take `"skills": {labour: level}` (schema enum 0–10), applied after seeding with XP 0 |
| Assignment prefers the most skilled free colonist with the labour enabled; ties by distance as today | `GlobalAssignment`: proposals carry `skill`; in the batching pass a job, when its turn comes, goes to its most skilled proposer whose slot is free (`_most_skilled_free()`); equal skill keeps the first in the old `_pair_before()` order (best score = nearest/oldest), so all-equal skills batch exactly as before. Scores, eligibility, brackets, aging and activation unchanged |
| No skill decay | Nothing lowers a level |
| Skills and XP saved (schema bump) | Schema v6: `entities[].skills`; `_v5_to_v6()` gives each colonist zero skills; validator checks labours, level range and `xp < xp_to_next[level]` |
| Shown in the colonist panel's labour table | `work_table_panel.gd`: under each priority button, the level and an XP `ProgressBar` (full at level 10), from the snapshot's new `"skills"` key |

Notes the reviewer should know:
- **`skills` is optional in the validator**, like `heldTool`. Every colonist the game spawns
  (`ActorTable.spawn`), seeds or migrates has it. Many tests build colonists by hand without
  it; such a worker works untracked: base speed, no XP, no bonus (the component's first
  invariant). That is also why most timing tests did not change.
- **No content-registry change.** `skills.json` is loaded because the registry loads every
  `content/*.json` with a schema. It is not in `DOCUMENT_KINDS` (required kinds), so the
  test fixture bundles without it keep loading. Without it the rules are empty and skills do
  nothing. `manifest.json` lists no files (it only holds `version`), so there is no manifest
  reference to add. The version is not bumped: that would make every existing save
  `content_version_mismatch`.
- **XP for site_work.** This bullet was corrected in review round 2.
  - A `site_work` job's work toil lasts the site's remaining `build_ticks`
    (`WorldState._resume_work_progress()`; the `work_ticks` 1 in `jobs.json` is not used).
  - Every builder adds one progress per tick, and the builder works until the site is built.
  - So a `site_work` job earns its XP once per builder per site, and `site_fetch` (build
    labour) earns per delivery.
  - Build speed does not scale with skill (see limitations).

## Hash coverage and determinism

- `skills` is part of the actor record, so `state_hash()` covers it like `labourTable`. A
  scheduler proposal's `skill` and the per-tick `_group_by_job()` map are runtime-only, never
  persisted or hashed.
- One new RNG draw site: `WorldSeeding._seed_skills()`, a local `RandomNumberGenerator`
  seeded `placement_seed ^ 0x5C11`, used only while a new world is created. It does not
  touch the simulation stream, the geography stream or the placement stream. Same seed, same
  skills and same `state_hash()` (tested).

## Known limitations

- Building speed does not scale with skill. A `site_work` job lasts until its site is built,
  and each builder adds one progress per tick at every level. Build XP is one `site_work`
  award per builder per site, plus one per `site_fetch` delivery; `xp_per_job.by_kind` can
  tune both.
- A resumed job keeps its stored remainder; a different colonist resuming it does not rescale
  it.
- Colonists that arrive later (an incident's migrant) start at level 0 everywhere; migrated v5
  colonists too.
- No skill-up event or message (UI beyond the labour table is a non-goal).
- `xp_per_job.by_kind` can only name the job kinds listed in `skills.schema.json` (every kind
  of today's `jobs.json`). A task that adds a job kind (F1, F2) adds a schema line if it wants
  an override; without one the kind earns `default`.
- Owner confirmation on the native build (the labour table's level and bar) is pending until
  after the merge.
