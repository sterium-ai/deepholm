## Owned paths and files changed

  re-hover after a wheel zoom.
- `game/scripts/viewer/map_view.gd`: **not changed**. Its `tile_at_local()` (floor of

- `game/scripts/tests/test_map_zoom_pointer.gd` (new).

## Root cause

The math of the mapping was consistent. `screen_to_tile` already went through
`map_view.get_global_transform_with_canvas()`, the same transform the map is drawn with.
The drift was a **stale hover**:

1. A wheel step calls `cancel_gesture()`, then `map_view.cancel_selection()`. That clears
   nothing visible right away, sets `_suppress_hover`, and does not re-read the tile under
   the pointer.
2. `zoom_at()` anchors the zoom on the pointer. Then `clampf(0.5, 3.0)` and `_constrain()`
   (the map edge clamp, and centring once the map is smaller than the viewport) move the map
   under a pointer that did not move.
3. So the highlighted tile stayed the one hovered *before* the zoom (or vanished on the next
   tick). It was drawn away from the pointer until the next mouse motion. The gap grows with
   the zoom step near the edges and limits, which is the "after zooming" drift the owner saw.

## Fix

- **One mapping.** `local_to_map(local_position)` is now the only conversion from a
  viewport-local point to map space. `zoom_at()` (its anchor), every forwarded mouse event
  (hover, drag, click) and the re-hover all use it.
- **The inverse lives next to it.** `tile_to_screen(tile)` uses the same child transform as
  `screen_to_tile`, so `screen_to_tile(tile_to_screen(t)) == t`.
- **Re-hover after a wheel zoom.** `_hover_at(event.position)` runs after `zoom_at()` in the
  wheel path. It feeds `map_view._gui_input` the same synthetic motion a real mouse move would
  send, converted through `local_to_map`. The highlight then follows the tile that is now
  under the pointer, with no B8 code edited.

## Test: `test_map_zoom_pointer.gd`

The test builds the debug scenario with the full UI at 1280x720 and the CHOP tool, then
checks:

- **Round trip.** For zoom 0.5 / 1 / 2 / 3, each with 3 pans (none, (-123,-79), (57,31)),
  and 4 tiles (corner, centre, far corner, near the bottom-left edge), it asserts
  `screen_to_tile(tile_to_screen(t)) == t`. That is the backlog acceptance.
- **Real input agrees.** For every tile visible on screen, a real `InputEventMouseMotion` is
  pushed through `root.push_input`. The test asserts `map._hover == t` and
  `map._preview_tiles == [t]`.
- **Wheel without moving the pointer.** From 3x, with the pointer near the top-left corner,
  it sends 10 wheel-down steps (down to 0.5x, where the map re-centres). After each step the
  highlight must be `[screen_to_tile(pointer)]`, or `[]` once the pointer is outside the map.
  The test also asserts that the tile under the pointer changed, so the check means something.

Proof that the test detects the bug: with the `_hover_at(event.position)` line commented out,
it fails as follows:

```
ERROR: wheel step 0 (zoom 2.50): highlight [] follows the pointer tile (18, 24)
...
ERROR: wheel step 4 (zoom 1.21): highlight [] follows the pointer tile (2, 19)
run_tests: 1 of 1 test(s) failed: test_map_zoom_pointer  [3s]
```

With the fix: `run_tests: all 1 test(s) PASS  [3s]`.

## Known limitations

- The re-hover happens only on a wheel zoom. Panning with the middle button or space+drag
  already sends motion events, and those already re-hover. A pan from the keyboard does not
  exist in the viewer today.
- A tick refresh does not move the camera, so it cannot cause drift.
