# R14 handoff — save schema reset to v1

> **In short:** Saves start over at `schemaVersion` 1 (`deepholm-save` v1). The state is
> written exactly as `main` wrote it at v27: same fields, nesting and values, with only
> the version number changed. A save from before the reset is refused with
> `unsupported_pre_release_save` ("unsupported pre-release save: … start a new game"). The
> 26 migration steps, 14 old fixtures, the legacy-build-job converter and the wall content
> rename are gone. The migration mechanism stays. The validator is split into one file per
> persisting module. Every persistence file is under 800 lines (the largest was 2,287), and
> the three "until R14" budget exceptions are removed.

- **Branch:** `antonelmejor50-hub/r14-reset-the-save-schema`
- **Base:** `63d3d5f` (`origin/main`, R12 merged). It was fetched again before the commit
  and had not moved, so no rebase was needed.
- **Commit:** the single R14 commit on top of the base (`git log -1`).
- **Decision record:** [ADR 049](../../decisions/049-save-schema-reset-v1.md).

## Save-format change (for A11 and every save consumer)

| | `main` (pre-release) | R14 |
| --- | --- | --- |
| envelope `format` | `"deepholm-save-v1"` | `"deepholm-save"` (`SaveIO.FORMAT`) |
| `state.schemaVersion` | 27 | 1 (`StateCodec.SCHEMA_VERSION`) |
| every other state field | — | **unchanged**: name, nesting and value format |
| JSON Schema | `schemaVersion: const 27`, legacy `approachRetiredActors` allowed | `const 1`, `approachRetiredActors` removed (no build has written it since ADR 033's revision) |
| reading a `"deepholm-save-v1"` envelope | migrated | refused: code `unsupported_pre_release_save` |

**Why the envelope string changed.** A pre-release save can carry `schemaVersion` 1 (an
old v1 shape) or 27, so the version number alone cannot tell it apart from a new v1 save.
The format string now names only the file type, and the version lives only in
`state.schemaVersion`. A later v2 save written by a newer build is therefore still reported
by this build as `save_from_newer_version`. This was my call: the backlog names the schema
"deepholm-save-v1", which I read as "deepholm-save, v1". If the owner wants a different
envelope string, it is one constant (`SaveIO.FORMAT`) and the v1 fixture would need to be
written again.

**A11:** replay snapshots compared with the save schema must expect `schemaVersion: 1`.
State snapshots (`StateCodec.encode()`) are otherwise identical to `main`'s. Envelopes
must use `"deepholm-save"`.

**Evidence that what is persisted did not change.** `docs/orca/handoffs/R14-write-save.gd`
runs the same 150-tick session (seed 1414, 3 colonists, 24×24, 6 chop/dig orders and a
zone) and writes it through `SaveIO.write_atomic()`. I ran it on `main` before touching
anything, which produced `game/scripts/tests/fixtures/pre_release_save_v27.json`, and again
on this branch, which produced `save_schema_v1_fixture.json`. Results:

- Both runs print `hash=1180613310`.
- The two `state` objects are equal except `schemaVersion` (27 vs 1): 31 top-level keys,
  compared as parsed JSON.
- The v1 fixture's state validates against `game-state.schema.json` with 0 errors (Python
  `jsonschema` 4.23.0, Draft 2020-12). The pre-release state's only error is
  `schemaVersion` ("1 was expected").

## What moved (move, not rewrite)

The moves were done with a script that cuts each top-level function, together with its
`##` doc, verbatim into its new file. Cross-file calls were then qualified with the class
name (`SchedulingValidator._valid_route_state(`, `StateCodec._encode_tile(`, …).
Validators `extends SaveCheck`, so the shared helpers (`_fail`, `_is_int`, `_valid_tile`,
…) are still called unqualified. `SaveIO` extends `SaveCheck` too.

**Check order kept.** `_validate_state()` runs, in this order: the top-level key and
required-field check, `schemaVersion`/`contentVersion`/`seed`/`tick`/`epoch`, then map,
items, objects, constructionSites, areaOrders, zones, nextZoneId, groundBerries,
workProgress, workProgressOwners, suspendedWorkProgress, pausedJobs, needJobAssignments,
rescueVictimAssignments, combatBlockedTargets, approachJobTargets, calendarAlerts,
toolFetchExcluded, toolItems, toolReservations, entities, inventory, jobs, scheduling, rng,
incidentScheduler, digFindRng. This is the order `main` used, so a multi-defect save
reports the same first error. Optional fields are still checked only when present.

**Deleted (legacy only):** the 26 `_is_schema_vN_state`/`_migrate_vN_to_vN+1` pairs and
their helpers, `_rename_wall_to_wooden_wall` + `_static_init` +
`WALL_RENAME_FROM_CONTENT_VERSION`, `migrate_legacy_build_jobs` (and its call in
`_read_and_verify`), `_valid_approach_retired_actors` and `approachRetiredActors` in the
allowed top-level set. Comments that justified optional fields with "an older save"
were shortened to what the field means now.

**Kept:** `SaveMigrations.migrate()` and `_migrate_step()` (no arms; any version below 1
gets `no_migration_available`), the content-rename registry
(`register/unregister/resolve`) with nothing registered, and the class doc's recipe for
v2.

## Hash coverage

`WorldState.state_hash()` (`world_state.gd`, not touched) still reads the same fields. The
four `StateCodec.*` helpers it calls (`_hash_colonists`, `_encode_combat_blocked_targets`,
`_encode_rescue_victim_assignments`, `_encode_approach_job_targets`) are now one-line
delegates to the moved functions, with identical bodies. Nothing was added to or removed
from the hash. The deliberately excluded fields are still excluded: faction maps, events,
`epoch` and `contentVersion`. The same session hashes `1180613310` on `main` and on the
branch.

## Known limitations

- Developers' local saves stop loading (by design). The game reports
  `unsupported_pre_release_save` and the player starts a new game. Owner confirmation on
  the native build is pending: after merge, an existing autosave should be refused with
  that message.
- Optional top-level fields stay optional on read (absent means empty or default), as on
  `main`. I did not tighten them to required, because that would change which saves load
  and is beyond a reset of what is persisted. `job.site` is likewise still optional on
  the wire.
- `StateCodec._restore_reroutes()` still has a branch for job kind `"build"`, which
  validation no longer lets through. It is unreachable but harmless. I left it, since it
  is decode logic outside the legacy converter I removed.
- Other docs still mention the old numbering and are outside these owned paths:
  - `docs/architecture/orders-and-movement.md:98` ("schemaVersion 26") and its
    construction "Persistence" paragraph (saves "written before construction sites
    existed");
  - `docs/architecture/foundation-for-breadth.md:90`.
  Suggested for R16 (doc pass). ADRs 005–047 are historical records and are left as they
  are.
- ADR number 049 could collide with an ADR from another task in flight (A2, A11). If so,
  whichever merges second renumbers it.
