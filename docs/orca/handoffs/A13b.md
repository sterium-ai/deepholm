## What changed

- **Schema v3: the save records its packs.** `StateCodec.encode()` writes `contentPacks`, the
  world's `ContentRegistry.packs()` in load order (`[{id, version}]`, `[]` on the base
  bundle), right after `contentVersion`. `contentVersion` now comes from the world's own
  registry instead of a fresh `ContentRegistry.new()`. `SCHEMA_VERSION` is 3, the
  `SaveMigrations` v2 -> v3 step inserts `contentPacks: []` (boot.gd has applied no pack roots
  before this, so every v2 save is base-only) and refuses a v2 state that already has one.
  Fixture `game/scripts/tests/fixtures/save_schema_v3_fixture.json`, written by
  `docs/orca/handoffs/A13b-write-save.gd` (the R14/A5 session, `hash=1180613310`, same as A5).
  It differs from the v2 fixture only in `schemaVersion` and `contentPacks`. The v1 and v2
  fixtures both migrate to it exactly (test).
- **Typed refusal, never repair.** `SaveIO.check_content_packs()` runs in `_read_and_verify()`
  after migration and the content-version check, and before the shape check (so a missing pack
  is named instead of one of its tiles being reported as an unknown tile). Any difference is
  `content_packs_mismatch` with `reason`: `missing`, `version`, `unexpected` (the session loads
  a pack the save lacks) or `order`. `SaveIO.read()` keeps `reason` on its result.
  `SaveManager.load_best()` reports the slot as skipped with that code. The viewer text
  `save.reason.content_packs_mismatch` names it ("made with different content packs").
- **Whitelists from the registry.** `SaveIO.content_rules(registry)` returns the tile ids,
  job kinds, need kinds and `max_world_size` from the session registry. `MapValidator`,
  `SchedulingValidator._valid_jobs()` and `EntityValidator._valid_entities()` take them as
  parameters, and the literals are gone. The job whitelist is now exactly `jobs.json`'s kinds,
  which drops the old literal's `craft`. No code creates a `craft` job (`grep -rn '"craft"'`
  finds only labour-table keys), and the owner approved this.
- **The session registry is passed in, not rebuilt.**
  - `SaveIO.read(path, content)`, `write_atomic(..., content)`, `StateCodec.decode(state,
    content)` and `StateCodec.content_version(content)` take an optional registry. null builds
    the base bundle, as `WorldState._init()` does, so existing callers and `TestAccess` keep
    working unchanged.
  - `StateCodec.content_of(world)` returns the registry a world was built on.
  - `SaveManager.new(dir, content)` holds the session registry (`get_content()`). It checks
    reads against it and checks each write against the saved world's own registry.
  - `boot.gd` passes `session_content()` to the save manager (1 line).
  - `SaveWiring.load_best()` decodes on `save_manager.get_content()` (1 line).
  - `ReplayLog.replay(after_tick, content)`, `validate(content)` and `from_dict(data, content)`
    take the registry. `replay()` refuses a start state with other packs using the same typed
    code, then decodes through `StateCodec.decode(start, registry)`. It cannot go through
    `WorldState.from_save_state()`, which has no registry parameter (and `world_state.gd` is at
    790/800 lines and not owned), so `replay_log.gd` changed, as the entry allows.
- **`StateCodec.encode()` is ~25x cheaper (intended).** On main every `encode()` called
  `content_version()`, which built a whole `ContentRegistry` from disk (read and validate every
  JSON file). Now it reads the world's registry. A probe on a 256x256 world (best of 5, same
  process, `docs/orca/handoffs/A13b-probe-encode.gd`) measured `ContentRegistry.new()` at
  20989 us, against 881 us for `encode()` on this branch: about 22 ms -> 0.9 ms per save. The
  owner confirmed this is correct and wanted.
  `SaveIO.read()`/`write_atomic()` also stop building a registry per call when given the
  session's: `MapValidator` used to build one per validation.
- **`test_command_preview` yardstick (owner decision, 2026-10-29).** The test checked that 144
  previews on a 256x256 world cost less than one `encode()`. That held only because of the
  registry rebuild: with ~0.9 ms per `encode()` it failed (984 us vs 721 us) with no preview
  regression. The owner chose to compare against a full `encode()`/`decode()` round trip,
  which is what the old hover path paid per tile (the test's own comment). The probe measured
  504856 us for that round trip.
  Reviews rounds 1 and 2 found the round trip alone looser than main's bound. Final shape,
  with two assertions:
  - the 144 previews cost less than one round trip (the owner's yardstick, kept);
  - they also cost less than main's own reference, reproduced exactly: one `encode()` plus a
    `ContentRegistry.new()`, which is what every `encode()` did before A13b (~21.9 ms on the
    host from the probe: 881 + 20989 us).

  So the check is as tight as main's and does not loosen as `decode()` slows down. Both sides
  are still timed in the same process, best of 5, which keeps the CI-runner robustness B1 added.
  The 144-command fixture and the state_hash check are unchanged.
- **Already done before A13b, so no change here:**
  - The debug scenario receives the session registry (`boot.gd:279`, from A16).
  - `WorldState` builds its `CalendarService` from the registry's `calendar` document
    (`world_state.gd:235`). The zero-argument `CalendarService.new()` that reads the file
    remains only in `test_calendar.gd`.
  - `SaveMigrations` builds no registry.

## Known limitations

- `tools/replay.ps1` and `CommandRecorder.read_file()` pass no registry. They replay on the
  base bundle only, so a replay recorded on packs is refused there with a typed error:
  `content_packs_mismatch`, or `invalid_replay` when the start state holds a pack id that the
  base whitelists reject. Neither file is in the owned paths. A pack-list flag for
  `replay.ps1` would be a follow-up.
- `game-state.schema.json` still lists the base bundle's tile, job and need ids as enums. A
  static schema cannot express ids that depend on the session, so its description says SaveIO
  reads them from the registry.
- Exact match only: the non-goals exclude loading onto other packs with repair, and that is not
  done. `CONTENT_PACK_ROOTS` is still empty, so the live game saves `contentPacks: []`.
