## Profile

Machine: Ryzen 7 9800X3D, RTX 5070 Ti, Windows 11, Godot 4.7.2, OpenGL Compatibility
renderer, vsync off, x1 (6 ticks/s), 600 s per run, one CSV row every 30 s.

**Column meanings:**
- `tick`: `world.tick()` time per frame.
- `refresh` (round-1 tables only): snapshot plus layer refresh.
- `callback` (round-2 tables): the whole `tick_driver.ticked` callback, i.e. `_on_ticked()`
  (recorder, autosave check, refresh). `callback max` is the slowest single callback in the
  row, and `saves` counts the autosaves completed in the row.
- `other process`: every other `_process` call, mostly the sprite layers' `advance()`.
- `render`: the frame's render time, measured by the profiler.

Those columns are mean ms per frame.

**Frame times are wall clock (review round 1).** `mean`, `p95` and `max` come from the time
between successive `_process` starts (`Time.get_ticks_usec()`). The first pass used `delta`,
which the engine clamps, so it hid the tails. `delta max` is kept as its own column to show the
difference.

## Profiler save isolation (review round 2)

Both blockers of review round 1 were in the evidence scripts. `game/scripts/boot.gd` is not
an owned path, so both fixes stay in `docs/orca/handoffs/`.

- **Saves.** Round 1's scripts used a plain `Boot`. Its `_ready()` resumes the player's newest
  save from `user://saves`, and its `AutosaveTrigger` writes there every 600 ticks and on focus
  out, pause and close. Both scripts now use `ProfileBoot`, a subclass of `Boot` that is given
  a profile dir (`user://b11-profile-saves` / `user://b11-memprobe-saves`, emptied at start)
  before it enters the tree. Its `_restore_from_save()`, which `_ready()` calls, loads nothing.
  Instead it swaps `save_manager` to that dir and re-attaches the autosave trigger, so the
  player's saves are neither read nor written. Both scripts assert that the trigger points at
  the profile manager. Before/after listings of `user://saves` for the round-2 runs are below.
- **Full tick callback.** The profile used to call `_refresh()` after each tick. That skipped
  `_on_ticked()`'s recorder and the autosave check, which writes the save synchronously every
  600 ticks (100 s at x1). The profile now runs `world.tick()` and then
  `tick_driver.ticked.emit()`, as `TickDriver` does, and times the whole callback. The new
  columns are `callback` (mean ms per frame), `callback max` (the slowest single callback in the
  row, which is where an autosave shows up) and `saves` (autosaves completed in the row).
  Results are in the round-2 Default and A9 tables above.

## Fixes (viewer)

1. **Settled colonist glides (`colonist_sprites.gd` `advance()`).** Before the fix, every frame
   re-applied the motion visual of every colonist, plus a full `queue_redraw()`, even when the
   colonist was standing still. Now a state whose glide has finished (`t >= 1`) and which loops
   no work animation is marked `settled` after its last application, then skipped. The mark is
   cleared by `_update_motion()`, which runs whenever a refresh sees a new tile, cargo or work
   kind. The redraw is queued only when something was applied. The drawn pixels are identical
   (covered by the existing glide, idle and work-loop tests).
2. **Actor animation clock (`actor_sprites.gd` `advance()`).** Before the fix, every actor was
   fully re-applied every frame. Now only the clock is advanced, `sprite.frame` is set from it,
   and a redraw happens only when some frame index changed. Position, flip and animation still
   change in `_track()` on refresh, as before.
3. **Held-tool badge removed** (owner decision). This also drops one SpriteRecord per colonist
   and one draw pass.

## Core findings (reported, not touched)

1. **The tick cost grows with game time on A9.** It goes from about 6 ms per frame at
   2–4.5 minutes to 20–35 ms per frame from 5 minutes on. Measured by wall clock, a single tick
   costs about 70 ms even in the steady window, and single frames reach about 1 s after 5 minutes
   (see the A9 wall-clock re-run). From then on the simulation cannot keep up with 6 ticks/s at 1000 colonists: it delivers
   about 4.5–5 ticks/s. The jump at t ≈ 300 s, around tick 1800, is reproducible in both runs. It
   looks like a phase change in the scenario (needs, jobs or routing once colonists reach some
   threshold), not a gradual leak. Suggested next step: a core task with the per-system tick
   breakdown (`tick_pipeline.gd`) on A9 around tick 1700–2000. Filed as **B13**.
2. **Static memory grows with flat object counts.** The growth is +67 MiB in 10 minutes on A9
   and +3.75 MiB per 3600 ticks in the core-only default probe. No Object or Resource
   accumulates, so the growth is in containers held by core objects (Arrays or Dictionaries
   that grow: logs, histories, caches). It needs a core task to name the container and cap it.
3. **Leaks at exit.** Both profiler runs end with "268 ObjectDB instances were leaked" and "61
   resources still in use". The memprobe has the same warnings, which is why both scripts exit
   with code 1 after printing `done`. These are exit-time warnings, with no growth during the
   run. They are probably reference cycles between core objects: a hygiene item, not a lag cause.
   Round 2 reads 201–202 at the profile's exit and 269 at the memprobe's.
4. **Autosave hitch (review round 2).** `SaveManager.save_autosave()` runs synchronously inside
   the tick callback every 600 ticks (100 s at x1). It takes 86–91 ms on the default scene and
   0.54–0.67 s on A9, in one frame each. At the default scene that is about 5 dropped frames
   every 100 s, visible as a short stall. Possible fixes are a cheaper serializer or a deferred
   or threaded write. Both are outside the owned paths (core persistence, plus `boot.gd`).
   Added to **B13**.

## Known limitations

- **Machine dependence.** The figures come from one fast desktop. 60 fps on the default
  scenario has a wide margin here (about 170 fps, capped). It is not measured on weaker hardware.
- **Occluded windows.** Windows throttles rendering for an occluded or minimized window. This
  hit the "before" A9 run after 210 s, so only 30–180 s is comparable for the viewer split, and
  the review-round-1 A9 re-run after about 90 s (its frame and tick columns are kept; its
  render and process columns are not used). The round-2 A9 run stayed visible and still shows
  the 1 s frames after t = 300 s, so occlusion does not cause them.
- **Concurrent load.** Another worktree's test suite (other Godot processes) was running on
  the machine when the round-2 runs started. The default run's p95 is flat from its first
  row, so the effect looks negligible, but it was not controlled.
- **A9 at 1000 colonists is not 60 fps,** with or without this change. It is bound by the core
  tick (findings 1–2), which is outside B11's scope by the owner's decision.
- **Settled-glide state changes.** The flag is cleared only through `_update_motion()`. Any
  future code that changes a colonist's drawn state without going through `_refresh_colonist`
  must clear it as well (documented in the `advance()` doc comment).
