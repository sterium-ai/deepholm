**Reading the A9 table:**
- **Steady window (90–270 s): the viewer fix works.** `other process` drops from about 4.95
  to about 0.6 ms per frame (−88%), and fps rises from about 66 to about 80.
- **"(n/a)" cells:** the before run's window was occluded from t = 210 s, so its render and
  process columns read 0 from then on. Only 30–180 s is comparable for the viewer split.
- **Render column:** `render` rises after the fix and `render_cpu` (3.2 vs 2.5 ms) barely
  moves. That reflects frame pacing: more frames are drawn, and each waits on present. It is
  not new draw work.

  20–35 ms per frame, and the world falls behind real time: 135–153 ticks per 30 s instead of

  several ticks, so most colonists' glides restart and few stay "settled".

## Fixes (viewer)

1. **Settled colonist glides (`colonist_sprites.gd` `advance()`).** Before the fix, every frame
   re-applied the motion visual of every colonist, plus a full `queue_redraw()`, even when the
   colonist was standing still. Now a state whose glide has finished (`t >= 1`) and which loops
   no work animation is marked `settled` after its last application, then skipped. The mark is
   cleared by `_update_motion()`, which runs whenever a refresh sees a new tile, cargo or work
   kind. The redraw is queued only when something was applied. The drawn pixels are identical
   (covered by the existing glide, idle and work-loop tests).
2. **Actor animation clock (`actor_sprites.gd` `advance()`).** Before the fix, every actor was
   fully re-applied every frame. Now only the clock is advanced, `sprite.frame` is set from it,
   and a redraw happens only when some frame index changed. Position, flip and animation still
   change in `_track()` on refresh, as before.
3. **Held-tool badge removed** (owner decision). This also drops one SpriteRecord per colonist
   and one draw pass.

## Core findings (reported, not touched)

1. **The tick cost grows with game time on A9.** It goes from about 6 ms per frame at
   2–4.5 minutes to 20–35 ms per frame from 5 minutes on (individual frames reach the 150 ms
   cap). From then on the simulation cannot keep up with 6 ticks/s at 1000 colonists: it delivers
   about 4.5–5 ticks/s. The jump at t ≈ 300 s, around tick 1800, is reproducible in both runs. It
   looks like a phase change in the scenario (needs, jobs or routing once colonists reach some
   threshold), not a gradual leak. Suggested next step: a core task with the per-system tick
   breakdown (`tick_pipeline.gd`) on A9 around tick 1700–2000.
2. **Static memory grows with flat object counts.** The growth is +67 MiB in 10 minutes on A9
   and +3.75 MiB per 3600 ticks in the core-only default probe. No Object or Resource
   accumulates, so the growth is in containers held by core objects (Arrays or Dictionaries
   that grow: logs, histories, caches). It needs a core task to name the container and cap it.
3. **Leaks at exit.** Both profiler runs end with "268 ObjectDB instances were leaked" and "61
   resources still in use". The memprobe has the same warnings, which is why both scripts exit
   with code 1 after printing `done`. These are exit-time warnings, with no growth during the
   run. They are probably reference cycles between core objects: a hygiene item, not a lag cause.

## Known limitations

- **Machine dependence.** The figures come from one fast desktop. 60 fps on the default
  scenario has a wide margin here (174 fps, capped). It is not measured on weaker hardware.
- **Occluded windows.** Windows throttles rendering for an occluded or minimized window. This
  hit the "before" A9 run after 210 s, so only 30–180 s is comparable for the viewer split.
- **A9 at 1000 colonists is not 60 fps,** with or without this change. It is bound by the core
  tick (findings 1–2), which is outside B11's scope by the owner's decision.
- **Settled-glide state changes.** The flag is cleared only through `_update_motion()`. Any
  future code that changes a colonist's drawn state without going through `_refresh_colonist`
  must clear it as well (documented in the `advance()` doc comment).
